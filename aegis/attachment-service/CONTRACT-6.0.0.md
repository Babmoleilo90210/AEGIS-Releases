# Потоковые вложения АЕГИС 6.0.0

Это новое расширение `ATTACHMENTS_V1`, отдельное от protocol1/Relay0.3.0. Старый Relay и его Limits/Operation не меняются. Клиенты5 не получают новый payload и поддерживаются минимум12 месяцев с фактической даты выпуска6.

Шифрование на клиенте: существующая библиотека Tink1.23.0, `AesGcmHkdfStreaming`, 32-байтный случайный ключ, HKDF-HMAC-SHA256, AES256-GCM, сегмент ciphertext1048576байт, offset0. Используется официальный формат Tink, без собственного nonce/шифра. Примитив привязывает сегменты к позиции, header и последнему сегменту. Ссылки: https://developers.google.com/tink/streaming-aead и https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming .

AAD: фиксированный домен `AEGIS-ATTACHMENT/v1`, canonical transfer UUID, sender/recipient account IDs (SHA256 публичных root Ed25519), точный plaintext size, один фиксированный suite ID. AAD не содержит filename; имя и MIME остаются в E2EE дескрипторе письма. Максимум500MiB=524288000байт plaintext. Ключ и descriptor передаются только внутри существующего E2EE сообщения Почты; они не являются частью серверного upload manifest и не передаются Community/News/Management. Долговременный identity key не шифрует поток непосредственно.

Для возобновления создаётся один приватный зашифрованный spool. Повторная загрузка использует те же неизменные bytes; повторное шифрование inplace или подмена segment под прежним header запрещены. Сбой до завершения шифрования требует нового spool/transfer/key. Открытый plaintext при расшифровании пишется в приватный temporary sibling; final file появляется атомарно только после проверки AEAD EOF, точного размера и полного digest. При ошибке temporary удаляется, гарантия физического стирания не заявляется.

Сервер не использует Tink и не обладает ключом файла: хранит immutable opaque chunks<=1MiB. Begin резервирует точный ciphertext total под quota/transferID; owner и recipient immutable. Put требует ciphertext chunk SHA256 и точную ожидаемую длину; повтор допустим только побайтово идентичный. Commit требует все chunks и полный ciphertext SHA256. Status возвращает bitmap/индексы; чтение доступно только owner/recipient с текущей действующей сессией. Квоты считают полностью reserved size, не только уже загруженные chunks. Неуспешная частичная загрузка не освобождает квоту до abort/expiration.

Абсолютный pendingTTL<=30дней с begin; недовыгруженные objects имеют TTL<=24часов. Ни status, ни повтор upload не продлевают TTL. Cleanup ограничен партиями. Имя файла/путь/URL никогда не берутся из клиентского manifest: только canonical UUID и фиксированный номер chunk. Symlink/необычный filesystem object отклоняется. Начальные safetyлимиты: максимум2 активные загрузки/отправителя,128transfers/account,4096общихobjects,8GiBglobal/2GiBperowner quota, минимум64MiBfree reserve. Эти административные лимиты не являются обещанием throughput.

Авторизация: Identity6 app=MAIL, текущие account/device/session/generation, audience ATTACHMENTS, scopes MAIL_SEND/MAIL_READ; fresh онлайн-проверка до каждого чтения/изменения и до каждой chunk выдачи. Хранилище не принимает client-derived approved/isAdmin. Production networkadapter без подключённогоIdentityguard обязан отказать в запуске/запросе. Локальные testguards — только unit/integration scope, не доказательство Tor/production.

Management/Identity API контракты согласуются отдельно. Полный500MiBtest сheap96MiB, tamper/truncation/wrongAAD/reorder, resumable immutable chunks/quota/restart/TTL — обязательны. Реальный Tor и старый установленный5клиент остаются отдельными gates.
