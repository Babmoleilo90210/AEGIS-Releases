# Почта 6.0: потоковые вложения и отдельные подтверждения

Этот отчёт дополняет IMPLEMENTATION-DESKTOP-6.0.0-RU.md. Он описывает реализованный клиентский код и фактически выполненные компонентные проверки. Он не заменяет общую приёмку релиза. `productionReady=false`.

## Потоковые вложения в рабочей Почте

В компоновщик и просмотрщик существующего MessengerApp подключён MailAttachmentManager600. При превышении прежнего настроенного inline-лимита выбранные файлы передаются потоково: до 500 МиБ суммарно на письмо, не более 64 файлов. Обычные письма и файлы в пределах прежнего лимита сохраняют прежний формат и Relay-совместимость.

Перед новой потоковой загрузкой клиент получает свежий, подписанный корневой идентичностью получателя ответ операции 102. Подпись связывает аккаунт, доверенный сервис вложений, лимит, случайный challenge и срок 60 секунд. Существующая операция 100 и её схема 1 не изменены. Старый или недоступный клиент не получает непонятный большой payload; пользователь видит причину отказа. Начало новой большой передачи требует работающего совместимого Mail peer. Постоянного кэша этих разрешений нет; произвольная отправка 500 МиБ полностью отключённому получателю не заявляется. После согласования зашифрованный объект и письмо могут ожидать получателя в пределах TTL.

Файл шифруется стандартным Tink AES-GCM-HKDF Streaming с сегментами 1 МиБ. Файловые ключи выводятся HKDF-SHA256 с отдельным фиксированным доменом и UUID передачи. На сервис уходят только шифротекст и необходимые транспортные метаданные. Ограниченные описатели версии PlainMessage 6 находятся внутри существующего подписанного AEGIS02A E2EE. Формат внешнего Relay-пакета не изменён.

В защищённом письме мастер-секрет дополнительно находится в стандартном LetterEnvelope с теми же паролем письма и FF1-кодом. Текст письма не заменяется структурированным контейнером. Любой результат FF1 даёт кандидат файлового ключа: новый синтаксический признак правильности кода не добавлен. Кандидат не проверяется при показе; подлинность файла проверяет потоковый AEAD при явном сохранении.

Ключи и состояния незавершённой загрузки сохраняются только в зашифрованном Mail sidecar. На диске очереди находятся шифротексты с закрытыми правами. Повтор использует прежние UUID и неизменный TTL, сверяет исходный файл по SHA-256 даже при сохранённых размере и времени изменения, а сервер подтверждает уже принятые части. Перешифрование хранилища переносит и проверяет ограниченные шифротекстовые очереди. После сохранения внешнего E2EE-пакета в существующей durable-очереди временная исходящая очередь очищается.

Получение происходит только по явному выбору нового файла. Проверяются сервис, отправитель из подписанного письма, получатель, срок, размеры, оба SHA-256 и потоковая аутентификация. Готовый файл публикуется атомарно без перезаписи. При отмене или ошибке частичный открытый файл не публикуется; незавершённые сетевые части остаются зашифрованными для повтора. Скачанное не запускается и не импортируется в личный архив автоматически.

Интерфейс показывает измеренные байты, поддерживает отмену и явную очистку незавершённой загрузки. Общий шифротекстовый spool ограничен примерно 1 ГиБ; устаревшие входящие части удаляются через семь дней. Успешное сохранение не вызывает ACK удаления серверного объекта: повторное сохранение возможно до TTL. Серверные квоты и TTL ограничивают удержание. Отдельной команды подтверждённого удаления с сервера и deferred ACK-очереди в этом изменении нет.

Публичные настройки задаются оператором через общий интерфейс Core: `core600/attachments600.properties`, ровно `onion`, `port`, `servicePublicKey` (Base64URL Ed25519). Capability и отдельный приватный app proof key берутся из допущенного процесса Mail, а не из файла настроек. Ненастроенная потоковая подсистема не блокирует обычную почту. Предварительный просмотр не выдаёт файловый ключ до разрешённого раскрытия защищённого письма; изменение FF1-кода и закрытие просмотра отзывают текущий кандидат.

Кнопки просмотра письма переведены на переносимую FlowPane, устраняющую усечение подписей при масштабе 200%. Действие «Ссылка → Взор» сохраняется после обновления оформления. Потоковые файлы учитываются в счётчике вложений поиска и списка. При архивировании такого письма пользователь явно предупреждается, что сохраняется только текст: файлы необходимо отдельно сохранить и импортировать. Автоматической пересылки удалённых ссылок/ключей нет.

## Критические подтверждения без передачи корневого ключа

В отдельном процессе Почты реализованы фиксированные цели OwnerTransfer, FirstDelegate и OwnerBootstrap. Для каждой обязательны допустимый purpose, подпись закреплённого Identity, app proof-of-possession, свежесть запроса, точное сравнение подписанного ответа live inspection и открытие именно аккаунта участника. Окончательное подтверждение требует отдельного, изначально выключенного флажка. Экран показывает полные отпечатки участников, назначаемую роль и срок; для Bootstrap также отпечаток Identity, одноразовое задание и границу локальной CLI оператора.

Почта перед подписью повторно проверяет действующую capability и срок, после чего подписывает только соответствующий канонический домен. В Core возвращаются открытый account key и подпись конкретного согласия. Пароль, recovery private key и корневой Mail private key в Core не возвращаются. Произвольного sign-RPC нет. Отмена проверяется до подписи и отправки результата.

OwnerTransfer подписывает отдельный role-bound `ownerTransferConsent`; FirstDelegate сохраняет существующий канонический `firstDelegateConsent`; OwnerBootstrap подписывает только `ownerBootstrapBytes`. Первая инспекция использует одноразовый app nonce, он не повторяется. Сервер обязан атомарно повторно проверить challenge, обе идентичности/устройства, generation, полномочия и необходимые независимые подтверждения при окончательном действии. Серверная реализация и её HTTP/CLI-проверки находятся в отдельном отчёте Identity.

Назначение первоначального владельца не завершается сетевым RPC из приложения: оператор завершает его локальной Identity CLI по публичному подтверждению. Challenge Bootstrap ограничен пятью минутами. Передача владельца и первое делегирование ограничены 120 секундами. Истёкшее согласование требуется начать заново.

## Жизненный цикл и миграция

Main Mail/Glas и временный процесс подтверждения удерживают RuntimeLease600 с начала до подтверждённого окончания работы. Возвращение из JavaFX не освобождает lease до завершения очистки/сохранения. Обычные автоматические updater-проверки и загрузки в компоненте Mail отключены: ими управляет Core.

Миграция Mail использует отдельный legacy-only ProfileSnapshot API: новые Core/Glas credentials и metadata не попадают в Mail legacy-app или его миграционную копию. Полный updater snapshot сохраняет эти новые состояния отдельно. Повторный прогон выявил реальный дефект восстановления отсутствующих metadata: создание пустого `mail600/migrated-profile6` блокировало миграцию. Исправление в ProfileSnapshot пропускает отсутствующие цели до создания родителей; проверка точного опубликованного 5.0.0 и связанные девять тестов повторно прошли.
