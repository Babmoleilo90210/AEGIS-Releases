# Серверные проверки АЕГИС 6.0.0

Результаты относятся к фактически выполненным локальным тестам. Среда — Ubuntu 24.04.3, PID 1 supervisord, Java 21.0.12.1, heap тестов 96 MiB. Это не Debian 13 и не нативная приёмка Windows/CachyOS.

Уникальных Java-проверок до Management client 46: 10 StreamingAttachmentCipher, 11 AttachmentStore, 1 LargeAttachmentStore600, 5 AttachmentHttpIntegration, 7 ManagementIdentityIntegration, 12 GlasSignalingIntegration600. Glas и Management повторно проверены вместе после исправления направлений contact-политик (19/19); старый отдельный Glas-прогон 11 тестов сохранён как предыдущий, не считается дополнительно. Повторные четыре HTTP-теста включены в ранний отчёт server-test-results и в более поздний http500-test-results; они не считаются дважды. Management client дополнительно даёт 7 уникальных проверок actual production HTTP boundary и точного wire-контракта; 14 client/server Management тестов повторно выполнены вместе. Management rate/busy regression добавляет ещё одну; Mail manager имеет три уникальных реальных HTTP-проверки (500 MiB, protected/FF1, четыре файла и повторное сохранение). Новый store-тест проверяет 2 uncommitted slots и 128 retained objects. Дополнительный load-сценарий — ещё одна уникальная проверка. Итого 59 уникальных Java-проверок по отдельным checkpoint-прогонам. Python: 23 всего, 19 PASS, 4 NOT_RUN (недоступны UID/chroot capabilities). У выполненных проверок failures/errors нет.

500 MiB действительно были зашифрованы и переданы через production AttachmentClient600/TorTransport, локальный SOCKS5 fixture, HTTP, реальный Identity HTTP и SQLite. Выполнены прерывания, перезапуск store, возобновление загрузки и получения, проверенное AEAD-расшифрование, ACK, отзыв поколения. Публичный Tor и два физических устройства не проверялись.

Management и его production HTTP client использовали реальный Identity HTTP и проверенные Owner/делегированного администратора, но systemctl заменён явным command recorder. Положительный результат не доказывает native root broker, systemd, AppArmor или реальное восстановление restic. Их статусы NOT_RUN.

XML/log сохранены для воспроизведения. Точные команды компиляции: Java 21 javac --release 21 для production common-protocol/identity-server/attachment-service/management-agent и соответствующих tests; JUnit Platform Console 1.13.4 execute --select-class с явно перечисленными JAR (wildcard JUnit classpath не используется). Полный build/check и привязка к итоговому commit выполняются отдельно.

Production Relay, feed и ключ владельца не изменялись. productionReady=false.

После исправления active-count лимит 2 относится только к незавершённым upload; committed файлы ограничены отдельно 128/account и byte quota. Actual manager HTTP тест с четырьмя файлами и повторным сохранением PASS. Автоматический ACK при сохранении не включён: объект остаётся доступен до TTL/явного удаления, это не single-download режим.

Focused checkpoint 30 дал 29 PASS и один FAIL экспорта load JSON (FileAlreadyExistsException после всех assertions); полный исходный log сохранён. Во время broad checkpoint параллельно менялся Identity/Core, sourceUnchanged=false. Изолированный повтор только load завершился PASS за 8.978 секунды при sourceUnchanged=true; он использовал новый уникальный output directory. Это не скрытый PASS полного frozen-commit build. `load/RESULT.json` содержит измеренные p50/p95, 100 регистраций/capabilities, 100 generation rotations/revocations, concurrency 4/16, signed 429, квоты и реальный FileStore high-water отказ. Физический ENOSPC, public Tor, systemd и две физические системы NOT_RUN. Нагрузочный сценарий не обещает производительность целевой ОС.
