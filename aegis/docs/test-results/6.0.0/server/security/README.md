# Проверка зависимостей и серверной авторизации 6.0.0

18 октября 2026 выполнены настоящие запросы официальных API OSV querybatch и GitHub Global Security Advisories для точных Maven-версий Gson 2.14.0, sqlite-jdbc 3.53.4.0, slf4j-api/nop 2.0.17. Все четыре OSV и четыре GHSA запроса получили HTTP 200; совпадений с уязвимыми версиями в этих ответах нет. Это ограниченный результат по фактически запрошенным базам, не доказательство отсутствия всех уязвимостей. Raw запросы, ответы и время сохранены в JSON.

NVD API вернул 290 SQLite keyword records, 2 Gson и 3 SLF4J; дополнительно запрошены CVE-2021-22569 и CVE-2022-25647 по ID, поскольку keyword search не дал полной истории Gson. Проверены 73 записи уязвимых CPE точных продуктов SQLite/SQLite JDBC/SLF4J/Gson с числовыми диапазонами. Для текущих версий совпадений и неопределённых числовых границ не найдено. Это не полный CPE inventory: необработанные/отложенные записи, новые CVE и иные продукты не получают автоматического статуса «безопасно». Среди рассмотренных современных SQLite CVE есть CVE-2026-11822/11824 до 3.53.2; реально загруженный JDBC JNI сообщил SQLite 3.53.4 и source ID в ACTUAL-NATIVE-VERSION.json.

Изначальные четыре JAR по байтам/SHA-256 совпали с официальным Maven Central: Gson и SQLite — опубликованный SHA-256; для SLF4J endpoint .sha256 дал 404, поэтому сами официальные JAR были отдельно получены и захешированы. Это проверка соответствия Central по TLS, не самостоятельная PGP-аттестация издателя. Одновременно JAR взяты из ранее проверенной владельческой базы и совпадают с её опубликованным подписанным комплектом.

Дополнительно для isolated mail-relay600 фактически проверен Password4j 1.8.4: официальный Central POM/SHA-256/JAR и LICENSE из project tag вернули HTTP 200; байты совпали. OSV и GHSA для точной версии вернули HTTP 200 без совпадений, NVD keyword HTTP 200 с нулём записей. Последнее не доказывает полноты базы. Password4j присутствует только в mail-relay classpath; transitive SLF4J выбран 2.0.17. Все пять JAR включены в обновлённый ограниченный SBOM.

Исходные лицензии получены из официальных project tags: Gson Apache-2.0; SQLite JDBC Apache-2.0 плюс сохранённый BSD-2-Clause notice Zentus; SLF4J MIT. Они включены в deployment/debian600/licenses и серверный tar. SQLite core public-domain dedication указан отдельным компонентом SBOM. JAR и все их внутренние notices сохраняются без изменений. Это ограниченный CycloneDX SBOM, не полный состав Debian/JDK/клиентского приложения.

Системные Debian 13 OpenJDK/Tor/Python/libsqlite3/restic/AppArmor/WireGuard в Work не установлены и не проверены как целевая ОС. Системный Python SQLite не равен JDBC SQLite. После hardening root helper вообще не импортирует SQLite: он копирует непрозрачные байты, а отдельный DynamicUser/systemd RootDirectory worker разбирает только одну БД без чужих файлов/ключей и сети. Реальные portable seccomp/refusal проверки PASS; UID/chroot/systemd/AppArmor и точные target patch levels остаются NOT_RUN. Нельзя использовать этот отчёт для снятия соответствующего release gate. Production backup, deployment и root-broker native tests не выполнялись. productionReady=false.

SERVER-AUTHORITY-REVIEW содержит SHA просмотренных исходников и фактические проверки account/app/device/generation/token/role/step-up. Положительная локальная проверка не доказывает внешний Tor, production Relay или нативную изоляцию.

Перед финальной упаковкой сверены Gradle runtime lockfiles: Gson также требует error_prone_annotations 2.48.0. Этот шестой внешний server JAR включён в classpath, SBOM и license inventory. Реальные Central POM/SHA256/JAR, project-tag COPYING, OSV и GHSA запросы вернули HTTP 200; байты совпали, exact-version OSV/GHSA ответы пустые. NVD отдельно для этого coord не запрашивался. Сохранён полный locked runtime, без предположения о допустимости удаления annotation dependency.
