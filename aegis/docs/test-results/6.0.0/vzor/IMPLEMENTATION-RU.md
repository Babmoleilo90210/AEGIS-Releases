# Независимый Взор 6.0.0 — фактически реализованная интеграция

`VzorLaunch600.openAuthorized(bundle, url)` запускает отдельную JVM с `VzorApp600`; приложение не получает `ClientSession`, identity, пароль, архив, accountId или IPC-capability экосистемы. В анонимный stdin однократно передаются случайный 32-байтный nonce и проверенный URL. Ответ привязан HMAC-SHA-256 к nonce, статусу и PID известного дочернего процесса. Nonce не попадает в аргументы, окружение или диск и очищается после подтверждения. Это подтверждение локального запуска доверенного дочернего кода, а не удалённая проверка личности и не защита от полностью скомпрометированной ОС.

`Detached` имеет `status()`, `managerPid()`, `managerAlive()` и намеренно не реализует AutoCloseable. Core/logout не владеет закрытием менеджера. Успешный запуск не оставляет канал контроля родителя; окно менеджера самостоятельно владеет своим временем жизни. `managerBusy()` — read-only guard для блокирования обновления АЕГИС при открытом менеджере; неизвестная ошибка проверки должна блокировать установку, а не разрешать замену работающих JAR.

Менеджер использует отдельный каталог `aegis-vzor-manager` / `AEGIS-Vzor-Manager`, собственный Tor DataDirectory, четыре отдельно резервируемых loopback-порта и ограниченные рабочие очереди. Конфигурация создаётся в памяти без загрузки client.properties АЕГИС; Relay пустой, хранилище переписки не открывается. Tor подготовки пакета не является Tor браузера и не выдаётся за его сетевой статус. Официальный Tor Browser сохраняет собственный штатный Tor.

Управление браузером и интерфейс используют существующие `SafeWebProcess` и `VzorView`: проверка закреплённой OpenPGP-подписи, проверенный установщик, bubblewrap/slirp4netns/Xephyr либо Windows Sandbox и fail-closed поведение сохранены. JavaFX WebView не используется. Каталог проверенного браузера 5.0 `aegis-safeweb` / `AEGIS-SafeWeb` сохраняется; cookies/история обычного системного Firefox не копируются. Обнаруженная системная копия без удостоверяемого происхождения не принимается: предлагается штатная проверенная установка. Режим без песочницы не добавлен; Windows Home остаётся ограничением существующего защищённого механизма.

Из окружения дочерней JVM исключены account secrets, proxy credentials, JAVA_TOOL_OPTIONS/JDK_JAVA_OPTIONS/_JAVA_OPTIONS, LD_PRELOAD и другие произвольные переменные. В отдельном окне скрыто действие импорта в личный архив: оно не может работать без передачи архива/ключей, которая намеренно отсутствует. Загрузки остаются отдельными и могут быть явно выбраны пользователем при импорте из приложения переписки.

Закрытие менеджера отменяет его операции, останавливает собственный download-Tor и SafeWebProcess и освобождает его блокировку. Повторное закрытие позволяет повторить незавершённую очистку. При неуспешном старте launcher завершает исключительно сохранённый объект Process; не ищет Tor/Java по имени, не сигналит PID из файлов и не обходит ProcessHandle.descendants. В данном контейнере PID namespace и /proc не совпадают, поэтому жизненный цикл проверен через реальный Process/ответ дочерней JVM/межпроцессную блокировку, а не потенциально чужой PID.

Реальная проверка: 19 JUnit PASS, включая запуск отдельной JVM, выход запускающей Core-fixture JVM при сохраняющейся блокировке менеджера, повторный запуск, тайм-аут/некорректный HMAC, фактическое завершение принадлежащего startup Process и сохранение посторонней JVM. Проверен запрет наследования профиля Core, схема URL, UTF-8/размеры/границы, блокировки, окружение, порты и безопасные сообщения. Wrapper JavaFX скомпилирован против существующего проверенного VzorView; полный новый продукт требует общего Gradle-прогона после интеграции.

Это не испытание реального браузера или сетевой изоляции: Windows 11, CachyOS Wayland/X11, реальный Tor/onion/HTTPS/DNS/WebRTC, Windows Sandbox, Polkit/UAC и обновление Tor Browser — NOT_RUN в данном прогоне. Запуск после реальной аутентификации Core зависит от подключения launcher в Core владельцем соответствующего модуля. `productionReady=false`.

Первичные источники Tor Project (прочитаны 2026-10-18):

- https://support.torproject.org/tor-browser/encountering-issues/known-issues/ — одновременные экземпляры Tor Browser не рекомендованы; система ограничивает один управляемый Взор и не заявляет проверенную совместимость с чужим открытым браузером.
- https://support.torproject.org/tor-browser/features/managing-identities/ — New Identity выполняется штатным браузером и останавливает текущие вкладки/загрузки; собственная неподдерживаемая IPC-команда New Identity не создаётся.
- https://support.torproject.org/tor-browser/security/using-tor-with-other-browsers/ — используется официальный Tor Browser.
- Документ по старому URL verifying-signatures в web-инструменте недоступен; это не скрывается. Действующий закреплённый ключ/проверка используются из исходной реализации 5.0.

Дополнение после общей интеграции: Core теперь вызывает openAuthorized после проверки Identity, VzorApp удерживает RuntimeLease600 до завершения JVM. Core/UI/Common согласованно скомпилированы в focused Gradle-прогоне51/51, но эти тесты не являются нативным запуском Взора. Исходные 19/19 выше сохраняют точную область JVM-fixture.
