# Локальное измерение offline Core 2.0.0 и 2.5.0

`productionReady=false`. Выполнены три независимых JVM-прогона каждой версии на одном Linux-контейнере с одним JDK 21, одинаковыми зависимостями и синтетическим workload. Все шесть итоговых прогонов завершили операции и проверки fixture с `PASS`. Это измерение офлайн-хранилища и архива; нативный запуск приложения, вход через сеть, Tor, «Взор», «Глас» и нагрузка на физическом устройстве — `NOT_RUN`.

База 2.0.0 — JAR, извлечённые из имеющегося опубликованного `base200.AppImage`. SHA Core/Protocol сверены с его `SOURCE-PROVENANCE-2.0.0.json`; runtime-source commit базы — `0a8efa98c1307ae2dc88c00d6b3208cdb260282b`. Проверяемая 2.5.0 — отдельная неизменяемая копия промежуточных `build/local-java21` Core/Protocol JAR. Точные SHA всех JAR, исходника benchmark и зависимостей записаны в `INPUTS.json`. После финальной пересборки сравнили каждую ZIP entry: все классы workload идентичны; изменился только updater `UpdateDiagnostic.class`, а Protocol entry bytes не изменились. Это сравнение находится в `SHARED-JAR-EQUIVALENCE.json`; сам benchmark нельзя объявлять исполненным на иной версии контейнера JAR.

## Метод

Последовательность JVM: 2.0/1 → 2.5/1 → 2.5/2 → 2.0/2 → 2.0/3 → 2.5/3. Каждая JVM запускается с `-Xms128m -Xmx768m -Djava.awt.headless=true`, создаёт независимые временные данные и удаляет только собственный fixture после закрытия объектов. Production-код не подменяется и не изменяется. Один и тот же benchmark `.class` компилируется против 2.0 и исполняется с каждой версией; фактические CodeSource URL записаны в raw JSON, чтобы исключить незаметную подстановку другой версии.

Vault содержит одну синтетическую identity и привязанный nickname, без писем, контактов и аватаров. Создание включает штатный Argon2id, генерацию identity, запись nickname и закрытие. Отдельно измерено повторное открытие с сохранением identity/nickname; это не сетевой login.

Архив содержит поток 32 MiB байтов0x41 без staging расшифрованного файла и 32 текстовых документа по 8192 байта. Используются штатные шифрование, атомарная запись, индекс и commit. Проверены SHA/размер бинарного объекта, число 33 объектов после reopen и единственный результат полнотекстового запроса по содержимому последнего документа. Пять последующих одинаковых запросов внутри JVM показаны отдельно от первого. Штатные случайные криптографические значения не фиксировались искусственным seed.

## Память и idle

Медианы трёх JVM, MiB. Heap/RSS — разные показатели. Peak RSS включает Argon2/JIT/импорт и не является постоянным расходом приложения.

| Показатель | 2.0.0 | 2.5.0 |
|---|---:|---:|
| Heap после явного GC и 500 мс | 8.41 | 8.44 |
| Linux RSS после idle | 198.73 | 200.82 |
| Peak RSS за жизнь JVM | 397.81 | 346.72 |

После операций отдельно вызван GC, выдержано 500 мс и измерен idle 2 с с открытыми vault и архивом. В итоговых шести JVM CPU counter доступен: прирост 0–10 мс за примерно 2 с. Это низкое разрешение короткого измерения, а не доказательство полного отсутствия фоновой CPU-работы. UI, сеть, Tor, браузер и звук в этих JVM не запускались; их idle-расход из этих данных не следует.

Первая попытка через `ProcessHandle.info().totalCpuDuration()` вернула `Optional.empty` в пяти из шести JVM. Её raw результаты и исходник сохранены в `attempt-processhandle-only/` с честным `UNAVAILABLE`. Причину проверили отдельно; итоговый benchmark использует отражение публичного `OperatingSystemMXBean.getProcessCpuTime`, затем допустимый fallback. Прямого linkage на необязательный `jdk.management` нет. Повтор вызван отсутствием CPU-метрики, а не выбором более выгодного времени.

## Повторение

Подготовить каталог `<runtime>` с подкаталогами `2.0.0/` и `2.5.0/`, в каждом `client-core.jar` и `common-protocol.jar`, и `dependencies/` с одинаковыми зависимостями из `INPUTS.json`. Не класть в dependencies дополнительные client-core/client-ui/common-protocol JAR. Скрипт перед исполнением проверит все SHA и исходник.

```sh
python run-core-comparison.py --runtime /absolute/runtime --inputs INPUTS.json --java /absolute/jdk21/bin/java --output /absolute/new-results
```

Результаты1в1 не гарантируются: новые криптографические соли, JIT, CPU scheduler и файловый cache остаются штатными. Raw `runs/*.json` и `logs/*.log` содержат фактические операции и времена; `SUMMARY.json` хранит агрегаты. Для другой сборки сначала подготовить новые точные inputs, не присваивать ей старые результаты.
