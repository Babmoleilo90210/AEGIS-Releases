# Независимое чтение новых transport границ

Область: ручной cross-review исходников CommunityHttpServer, CommunityAuth, CommunityClient, ClientSession.adminStepUp, VoiceGrantCache и операторского CLI. Это проверка кода, не результат DNS/network capture, работающего onion-сервера или native acceptance. Автоматическое исполнение HTTP/client сценариев фиксируется отдельными отчётами общего прогона.

Обнаруженные и исправленные в исходниках взаимодействия:

- Серверная regex действий не принимала underscore нового голосового batch API; приведена к клиентскому контракту. HTTP-регрессия добавлена владельцем транспорта.
- Ответ привязан не только к service audience/nonce, но и к actor плюс digest точного запроса. Это закрывает подмену результата другим запросом с тем же nonce.
- Клиент проверяет closed повторно перед кэшированием. Флаг закрытия выставляется до обхода активных sockets; открывающий callback закрывает появившийся после этого socket. Есть ограничение числа RPC и абсолютный deadline, включающий SOCKS.
- Epoch и результат обычного серверного действия формируются в одной SQLite транзакции. Агентские сетевые операции выполняются вне внешней транзакции и перепроверяют поколение до отдачи результата.
- Step-up контекст v2 включает service fingerprint; клиент не подписывает произвольные предложенные байты.
- Первоначальное подключение TOTP обычного пользователя не заменяет существующий фактор и не доступно глобальному администратору.
- Счётчик неправильного фактора сохраняется после отката внешней HTTP-транзакции. Отдельный focused JUnit воспроизводит такое вложение.
- Обычное вступление/выход не отменяет proof другого администратора. Токен связан с factor version, а права проверяются непосредственно при действии.
- Служебное AGENT_WORK назначение не может заблокировать одного из двух действующих администраторов; worker identity не повышается в администратора.
- Отображаемое имя общего состава синхронизируется отдельным self-only действием без mass assignment identity, clearance или badge.

- Обнаружен HIGH: изменение собственной назначенной роли или её предка могло само авторизовать новые права и уровень, потому что проверка читала уже изменённый граф. Два реальных SQLite/JUnit воспроизведения до исправления завершились ожидаемым FAIL. Исправлено: разрешения, clearance и статус администратора фиксируются до записи в той же транзакции. Повторный прогон 46 тестов PASS включает self-role, ancestor, clearance-only и разрешённое переименование. Старые FAIL сохранены отдельно и не выдаются за результат исправленной версии.

- Максимальные Unicode payload могли переполнить ответ списка критических заявок из-за 100 записей и двух aliases. Исправлено: стабильная пагинация по UUID, страницы до 10, nextAfter. Настоящий SQLite fixture из 100 строк с payload по 65536 символов CJK полностью прочитан десятью страницами через production handler; каждый полный envelope успешно разобран StrictJson внутри лимитов 8 MiB/8192 nodes.

Проверенные проектные свойства: production client connector использует onion через loopback Tor SOCKS; DNS для onion не выполняется локально; GET/публичный bind центрального origin не включены; JSON не выполняет полиморфную десериализацию; точная подпись проверяется до разбора body; nonce сохраняется до обработки; протокол писем и pinned release key не меняются новыми RPC.

Границы: эти свойства исходников не доказывают запуск реального Tor, отсутствие сетевых утечек в целевой ОС, безопасность полностью скомпрометированного host или production-config. Audit HMAC без внешнего checkpoint не гарантирует обнаружение rollback всей БД/усечения корректного хвоста. Поддержка Windows server ACL требует отдельного испытания. Операторский deployment не выполнялся.
