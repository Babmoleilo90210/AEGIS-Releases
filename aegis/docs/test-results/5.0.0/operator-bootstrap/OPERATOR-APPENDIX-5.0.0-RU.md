## Первое подключение общей системы и новостного узла

Сервер организаций, новостей и библиотеки развёртывается отдельно. Установка настольного АЕГИС сама его не запускает. После bootstrap двух независимо проверенных Ed25519 identity и разных TOTP оператор запускает центральную службу на `127.0.0.1:38150`, настраивает отдельный Tor onion service и передаёт пользователям его onion-адрес и проверенный открытый ключ сервиса (Base64). Оба значения вводятся в настройках общей системы клиента. Nickname не назначает административных прав. Production Relay и его onion-каталог при этом не меняются.

### Сначала зарегистрировать identity worker, затем выдать полномочия

1. Под отдельным системным пользователем узла создать служебную пару командой `bin/news-worker --generate-key /etc/aegis/worker-identity`. Сохранить напечатанный SHA-256; проверить его независимо. Ключ обычного пользователя или администратора для worker не подходит.
2. С правильным onion-адресом, закреплённым открытым ключом сервиса и доступным Tor выполнить указанный в SERVER-DEPLOYMENT-PROPOSAL запуск worker с `--once` **до** выдачи роли. Первый подписанный `agent.worker.claim` регистрирует публичную identity, но закономерно отклоняется из-за отсутствия полномочий. Это не успешное получение задания. CLI выводит общее сообщение о недоступном задании; его exit code сам по себе не доказывает регистрацию, поскольку сетевые ошибки обрабатываются так же.
3. Два администратора с действующим TOTP создают глобальную роль только с `AGENT_WORK`, согласуют её назначение точному fingerprint worker и включают эту же identity в списке рабочих узлов. Каждое глобальное действие проходит отдельную критическую заявку и независимое подтверждение. Не добавлять worker в организации и не назначать ему другие роли. Если назначение отклонено из-за отсутствующей identity, проверить onion/Tor/ключ и повторить шаг 2.
4. Повторить `--once`. Теперь разрешённый claim принимается; при выключенном агенте или отсутствии задания допустим ответ без задания. Только после этого включать постоянную службу. Это ещё не доказательство успешного обхода реальных источников или качества модели.

Порядок подтверждён отдельным испытанием с финальными production-классами HTTP, WorkerCoordinatorClient, Ed25519 и настоящей временной SQLite: отказ первого claim сохраняет identity в завершённой транзакции, видимой из независимого подключения; последующие реальные двухадминистраторские операции позволяют второй claim; identity сохраняется после повторного открытия БД. Подключение теста было loopback seam, не настоящим Tor. Тестовые БД и ключи в публичный комплект не включаются.

### Отдельная identity издателя и конфигурация

До включения агента подготовить отдельный аккаунт издателя и один раз подключить его клиент к выбранному Community-сервису, чтобы зарегистрировать его существующий публичный ключ. Два администратора назначают этой identity минимальные глобальные `NEWS_CREATE` и `NEWS_PUBLISH`. `NEWS_GLOBAL_PUBLISH` выдаётся только при явно разрешённой всеобщей публикации. Издателю не выдаётся `AGENT_WORK`; его приватный identity key не передаётся worker или центральному CLI. В конфигурации агента указывается точный fingerprint издателя, а не nickname.

Администрация регистрирует нормализованные города, законно доступные источники и независимые группы источников, выбирает модель и endpoint, задаёт верхние тарифы и лимиты запросов/токенов/денег, затем включает агент. Изменения критической конфигурации подтверждает второй администратор. Без модели, источников и необходимых прав публикация не будет работать; их отсутствие нельзя считать успешным запуском ИИ.

### API-секрет нужен центральной службе и worker

При внешнем провайдере конфигурация содержит только имя переменной, например `AEGIS_NEWS_API_KEY_MAIN`. Её фактическое значение оператор задаёт в защищённом окружении **обоих** процессов: worker выполняет исходный анализ, а центральная служба отдельно формирует и проверяет редакционный результат. Для каждого процесса можно использовать отдельный ограниченный ключ провайдера, сохранив одинаковое имя переменной из `credentialRef`. Один лишь секрет worker не включает центральную проверку.

Для центрального systemd-шаблона оператор создаёт закрытый root-owned файл `/etc/aegis/community-model.env` (0600) и drop-in через `systemctl edit aegis-community.service`:

```ini
[Service]
EnvironmentFile=/etc/aegis/community-model.env
```

В закрытый файл записывается значение выбранной переменной `AEGIS_NEWS_API_KEY_...`; секрет нельзя добавлять в командную строку, Git, release, diagnostics или этот отчёт. Worker использует уже предусмотренный `/etc/aegis/news-worker.env` с закрытыми правами. После изменения unit/drop-in выполнить `systemctl daemon-reload` и контролируемо перезапустить соответствующую службу. Проверить работоспособность и собственные лимиты расходов у провайдера. Ни эти команды, ни развёртывание автоматически не выполнялись.

При Ollama модель должна быть установлена и доступна на разрешённом literal-loopback endpoint каждого хоста, который выполняет анализ: центрального и worker. Если процессы находятся на одном хосте, возможен один согласованный локальный экземпляр с разными системными пользователями. Сам АЕГИС не загружает модель и не превращает localhost другого хоста в удалённый endpoint.
