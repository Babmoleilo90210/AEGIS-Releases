# Проверка нативных зависимостей АЕГИС 5.0.0

Проверка выполнена 15 октября 2026 года. Это дополнительный аудит зависимостей, а не нативная приёмка Windows 11 или CachyOS KDE. Общий результат — `PARTIAL_REVIEW_REQUIRED`; `productionReady=false`.

## Фактически исследованные входные данные

Исходный опубликованный commit 2.5.0: `699a3260fa456a40d4d16d3b711c957b088f9ab3`. Архив Windows и извлечённый AppImage ранее сверены побайтно с опубликованными артефактами; подтверждение находится в `../../5.0.0/packaging/REUSED-BASE-VERIFICATION.json`. `BASELINE-NATIVE-PROVENANCE.json` сохраняет build-inputs и ранее проверенные реестры Java/аудиобиблиотек. `NATIVE-DEPENDENCY-INVENTORY-5.0.0.json` содержит реальные SHA-256 файлов и результаты команд. `SOURCE-PROVENANCE-5.0.0.json` сохраняет исходные URL, даты, размеры и хеши сетевых ответов с краткими квалифицированными выводами. Полные полученные веб-страницы и исходные сетевые документы не включены в репозиторий или релиз; точные байты сохранены отдельно для воспроизведения аудита.

## Найденная проблема OpenSSL и проверенное обновление

Официальное уведомление OpenSSL от 29 сентября 2026 года подтверждает **CVE-2026-84782, HIGH**: ошибка повторной отправки сообщений DTLS может раскрыть память или привести к отказу в обслуживании. Ветка 3.5 исправлена в **3.5.9**. См. [официальное уведомление](https://openssl-library.org/news/secadv/20260929.txt) и [страницу ветки OpenSSL 3.5](https://openssl-library.org/news/vulnerabilities-3.5/). URL, время получения, размер и SHA-256 точных ответов находятся в `SOURCE-PROVENANCE-5.0.0.json`; полные ответы сохранены отдельно от репозитория и релизного комплекта. В исходной базе действительно присутствует 3.5.8. Остальные записи страницы 3.5 также требуют учёта: успешная Maven-проверка не распространяется на OpenSSL.

Для оценки достижимости исследован официальный исходный файл Tor на **точном commit из работающего бинарника**: `torproject/tor@3c575400909efe6599d88e61e7daf0012655ca44`, `src/lib/tls/tortls_openssl.c`. Он создаёт контекст через `SSL_CTX_new(TLS_method())`, устанавливает минимум TLS 1.2 и использует `BIO_new_socket`. Динамические импорты проверенного Linux Tor содержат `TLS_method`, без `DTLS_method`, `DTLS_client_method` или `DTLS_server_method`. Это подтверждает отсутствие DTLS-пути у исследованного TLS-контекста Tor. Оно не объявляет библиотеку OpenSSL целиком неуязвимой и не заменяет установку доступного исправления.

Найден актуальный официальный **Tor Browser / Expert Bundle 15.0.25**, опубликованный 12 октября 2026 года. Официальный [changelog Tor Project](https://blog.torproject.org/new-release-tor-browser-15025/) указывает **Tor 0.4.9.14 и OpenSSL 3.5.9**. Подтверждающая запись `tor-blog-latest` в `SOURCE-PROVENANCE-5.0.0.json` сохраняет дату и SHA-256 полученного ответа; полный HTML не включён в публичный комплект.

Прямые `dist.torproject.org` и `aus1.torproject.org` в данном окружении возвращали HTTP 200 с 195-байтным документом `Site Unavailable`. Эти обращения явно отмечены `NOT_RUN_SITE_UNAVAILABLE`. Для получения **официально подписанных байтов** использовано прежнее документированное зеркало Tor `ftp.acc.umu.se/mirror/torproject.org/dist/torbrowser/15.0.25/`. Листинг зеркала служил только для обнаружения файлов. Подлинность проверена существующим производственным `TorBrowserSignature` и отдельно GPG: полный закреплённый primary fingerprint **EF6E286DDA85EA2A4BA7DE684E2C6E8793298290**, подписывающий subkey **022DA248432D2A0E0F54E65E316C1FACD62D07D9**, без изменения корня доверия.

Оба хеша также совпали с отдельно подписанным `sha256sums-signed-build.txt`. Полные detached signatures, результаты Java/GPG, сведения об источниках и **все пути/размеры/хеши/различия** членов архивов находятся в `tor-patch/`. Архивы распакованы в отдельные каталоги только после успешной проверки подписи; абсолютные пути, `..`, ссылки и специальные файлы отклонялись. Рабочие каталоги и staging приложения этой проверкой не изменялись.

Реальный Linux `--version` проверенного нового Tor подтверждает **0.4.9.14 / OpenSSL 3.5.9**. Проверка конфигурации и запуск процесса с `DisableNetwork 1`, выключенными SOCKS/ControlPort и последующим SIGTERM завершились успешно, exit 0. Первая попытка с `/dev/null` вместо обычного torrc была отклонена Tor; исходный результат и успешное повторение сохранены. Это проверка процесса с отключённой сетью, **не** доказательство подключения Tor, DNS-изоляции или нативной приёмки. Windows: подпись и статические версии проверены, выполнение `NOT_RUN`.

Версионное совпадение HIGH исправлено в проверенных новых входных данных. Для признания исправления в конечном продукте требуется включить эти точные байты в финальные пакеты, обновить реестры, повторить связанные проверки менеджера Tor и проверить готовые артефакты. Отдельная запись `VERIFIED-PATCH-INPUTS.json` намеренно имеет `PATCHED_IN_VERIFIED_CANDIDATE_NOT_YET_STAGED` и не выдаёт промежуточную проверку за итоговую сборку.

## Границы остальных результатов

Получены официальные changelog/libsodium, страницы выпуска Opus 1.6.1 и SpeexDSP 1.2.1, а также GitHub Security Advisories API соответствующих официальных проектов. Возврат пустого массива API означает отсутствие записей в этом конкретном источнике, а не доказанную свободу от всех CVE. Ветка libsodium `1.0.22-stable` изменяема; источник и точный архивный хеш записаны отдельно от возвращаемой версии API.

Для нативных upstream-версий не найдено надёжного полного соответствия экосистеме OSV: версия исходника не является версией пакета Debian/Alpine с его исправлениями. Неподтверждённое сопоставление не выполнялось. Полная CVE-проверка libsodium/Opus/SpeexDSP/Libevent и Java остаётся `NOT_RUN_EXACT_NATIVE_ECOSYSTEM_MAPPING` либо `NOT_RUN` при недоступности официальной страницы. Это открытая область аудита, а не PASS.

Положительный контроль Maven OSV расположен в `../positive-control/`: настоящий запрос для заведомо уязвимого Log4j 2.14.1 вернул семь advisory и CVE-2021-44228. Этот компонент не включён в АЕГИС, не скачивался и не запускался; контроль проверяет работоспособность получения advisory.

## Повторение

Инвентаризация: `python tools/audit-native500.py --linux-root <проверенный-AppImage-root> --windows-root <проверенный-Windows-root> --source-cache <сохранённые-первичные-ответы-и-FETCH-json> --base-verification docs/test-results/5.0.0/packaging/REUSED-BASE-VERIFICATION.json --out <каталог-публичных-метаданных> [--raw-archive <отдельный-каталог-полных-ответов>]`. Полные ответы по умолчанию не копируются; необязательный `--raw-archive` обязан находиться вне каталога публичного результата.

Проверка подписи новых архивов воспроизводится сохранённым `tor-patch/VerifyTorPatch.java`, JDK 21 и classpath с собранным `client-core`, его ресурсами и проверенными Bouncy Castle JAR. Java-класс вызывает производственный `TorBrowserSignature.verify(archive, asc)`; полный вывод каждой проверки сохранён. Приватные ключи не использовались.
