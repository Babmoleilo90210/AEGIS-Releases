# Glas Signaling 6.0.0 — согласованный протокол и границы

Это отдельный onion origin, а не замена старого Relay. Он не принимает аудио, TLS certificates/media offers, содержимое писем или приватные ключи. Транспорт аудио остаётся прямым onion P2P с существующим TLS 1.3 после принятия вызова и проверки собеседника. Регистрация адреса сама по себе не означает завершённую аутентификацию голосового канала.

Все запросы POST `/glas/v1` проходят app PoP над SHA-256 точных байтов запроса через действительный Identity `authorizeDigest(..., "glas.call", ...)`. Приложение строго GLAS, scope VOICE_CALL, текущее поколение/устройство/lease. Другие app capabilities не принимаются. Сервер не доверяет client isAdmin, nickname, contact flags или unsigned generation.

Root-signed `Delegation`: Identity audience, account public key (44-byte canonical Ed25519 X.509), device ID, generation, GLAS app public key, issued/expires (не более 24 часов и срока capability), nonce и подпись account root. Домен AEGIS-GLAS-DELEGATION/v1. Подпись запрашивается только как типизированное согласие в Почте; root private key в Глас/сервис не передаётся. Delegation не даёт прав переписки или подписи произвольных сообщений.

App-signed `Endpoint`: pin signalling-сервиса, SHA-256 delegation, строго Tor v3 onion, порт, issued/expires (не более 120 секунд), nonce и подпись GLAS app. Домен AEGIS-GLAS-ENDPOINT/v1. Это криптографическая аттестация соответствия адреса указанному аккаунту/app, не активное доказательство достижимости onion и не разрешение пропустить последующий TLS/identity handshake. Core создаёт адрес через собственный Tor ADD_ONION. Сервис никогда не открывает supplied network address.

REGISTER передаёт delegation/endpoint и два ограниченных списка ID разрешённых контактов: входящих и исходящих. Неизвестные пользователи по умолчанию запрещены. Эти списки не являются глобальной адресной книгой и не позволяют организации самостоятельно выдавать глобальные полномочия. Организационные исключения требуют отдельного проверенного Community authority bridge; неподтверждённое исключение отвергается.

LOOKUP содержит точный ID собеседника, его уже закреплённый root public key и подписанное направление: исходящий либо проверка входящего. Для входящего проверяются local.incoming и remote.outgoing, для исходящего local.outgoing и remote.incoming; разрешение обратного звонка не выдаётся. Требуются действительная регистрация обоих участников и соответствующие направлению разрешения; обе актуальные Identity capabilities проверяются online. Отсутствующий, отозванный, запрещённый или истёкший target имеет одинаковый отказ. Возвращаются только подписанные delegation/endpoint, без политик, токенов или остальных контактов. UNREGISTER идемпотентно удаляет собственную регистрацию.

SQLite хранит только краткоживущие публичные привязки, app capability и contact allowlists, не звук/ключи. Каталог 0700, файлы 0600, NOFOLLOW, отдельный процессный lock, secure_delete, максимальный размер запроса 48 KiB, список ≤256 ID на направление, 10000 регистраций, два workers/очередь 8, 300 запросов в минуту, абсолютный срок RPC 15 секунд. TTL очищается ограниченными пачками. Часы не могут откатывать уже проверенный срок в одном процессе; сохранённый floor проверяется при повторном открытии.

Initial authorization свежая; повторный successful live recheck в пределах одного короткого RPC может кэшироваться не более 250 мс (общая библиотека IdentityRemoteAuthority), без offline fallback. Полученная ранее аттестация может оставаться видимой у контакта до своего срока; клиент обязан заново проверять live generation и прекращать сессию при отзыве. Сервис один не доказывает реализацию client call lifecycle, NAT/physical-device Tor, microphone consent или нативную приёмку.

Оператор сигнального сервера технически может наблюдать краткоживущие contact ID и пары lookup-запросов. Они не объявляются скрытыми от сервера; журналы приложения эти значения не сохраняют. Tor не исключает временную корреляцию. Одобрение входящего вызова, pinned peer TLS и отсутствие захвата микрофона до принятия проверяются отдельно в клиенте. Формат onion проверяется по официальной спецификации Tor https://spec.torproject.org/address-spec (version 3 и SHA3-256 checksum); проверка не доказывает достижимость или владение onion private key.
