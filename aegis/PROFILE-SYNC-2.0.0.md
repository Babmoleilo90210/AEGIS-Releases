# Публичные профили и аватары

Существующий протокол уже содержит PublicProfile, signed revision, capability bit 1 и подпись identity. Клиент публикует изменённый профиль и получает профили контактов по очереди; кэш шифруется LocalStore. AvatarCodec нормализует разрешённое изображение в PNG, ограничивает вход и размеры перед декодированием; метаданные оригинала не передаются. Проверяются подпись, ключ контакта, revision и размер. UI использует проверенный кэш, а не чужой локальный аватар.

Исправление: новые профили публичны по умолчанию. Выбор существующего пользователя сохраняется. Удаление/изменение отмечают profilePending, синхронизация повторяется штатно; offline показывает последний подписанный кэш.

Добавлен интеграционный сценарий A/B: загрузка PNG, получение B, изменение и обновление, скрытие, удаление, восстановление, offline reopen. Используется настоящий SQLite Relay и wire protocol через управляемый SOCKS harness. Это не доказательство работы production Relay через Tor. На пользовательском скриншоте написано «Сервер поддерживает базовую почту»; это согласуется с capability=0. Фактическая capability production-сервера здесь не проверялась.

Если production Relay не поддерживает profile capability, клиент не может исправить доставку аватара без сервера. Предложение для отдельного разрешения: проверить версию/capability, установить совместимую реализацию signed PublicProfile существующего protocol 1 в staging, проверить два аккаунта через Tor, visibility redaction, anti-replay, ограничения размеров/хранилища; только затем согласовать production deployment. Ни сервер, ни протокол этой работой не изменены.

Переименование nickname: текущая регистрация привязывает имя к identity и каталогу сервера, операции rename нет. Нельзя молча заменить локальное имя или создать новый identity. Требуется отдельная спецификация alias/rename с неизменным userId/public key, уникальностью, авторизованной атомарной серверной операцией, обновлением контактов и migration/rollback. До согласования поле read-only.
