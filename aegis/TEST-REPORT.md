# Проверки АЕГИС 0.2.0

Дата: 3 октября 2026. Сборочная среда: Linux x86_64 (Ubuntu 24.04), Java 21.0.12.1. Исходники основаны на АЕГИС 0.1.0. Это собранная предварительная версия: обязательная приёмка на чистых целевых ОС ещё не выполнена.

## Выполнено

| Проверка | Результат |
|---|---|
| Gradle build, Java 21 | Успешно |
| common-protocol | 4 теста, 0 ошибок |
| client-core | 22 теста, 0 ошибок |
| relay-server | 3 теста, 0 ошибок |
| integration-tests | 4 теста, 0 ошибок |
| Официальный набор libsodium | 101 тест, 101 PASS |
| Windows JavaFX staging | Успешно |
| Настоящий JavaFX GUI в Monocle | Экраны сервера, входа, регистрации и чата отрисованы; текст автоматически открыт из ciphertext |
| Tor Expert Bundle: direct и Snowflake | Оба torrc приняты поставляемым `tor --verify-config`; неправильный `front=a,b` запрещён |
| Независимый процесс relay 0.2.0 | Регистрация, offline-доставка, файл 2 MiB, ACK, дедупликация и TTL прошли |
| Независимый исходный relay 0.1.0 | Те же проверки с новым клиентским кодом прошли без изменения protocol 1 |

Все 33 теста приложения завершились без пропусков. Они проверяют неверный ключ, подмену ciphertext/подписи, nonce, TTL после первой доставки, срок очереди, потерянный ACK, дубликаты, P2P и relay fallback, отсутствие clearnet fallback, ограничения размеров, приватное хранилище, backup, Windows-имена файлов, onion-адрес и открытый/закрытый режим регистрации.

`ReleaseProcessSmoke` дополнительно запускает реальный отдельный JVM relay, регистрирует два тестовых аккаунта, шифрует текст и 2 MiB вложение, держит получателя offline, получает и проверяет файл, подтверждает ACK и удаление по TTL. Контрольный plaintext и приватный PKCS#8 ключ не встречаются в записанном relay-трафике и проверенной БД. Это конкретная проверка, не математическое доказательство отсутствия всех возможных утечек.

Транспорт между клиентами и relay в этих испытаниях — тестовый SOCKS на loopback. **Настоящая сеть Tor и разные физические сети здесь не проверены.** SOCKS-стенд и Monocle не включены в готовые приложения. Для проверки 0.1.0 использованы исходные relay/common JAR; повреждённый локальный архив SQLite восстановлен той же версией 3.53.4.0 из закреплённого Maven-артефакта.

Входные ZIP/tar проверены закреплёнными SHA-256. Изменившийся upstream tarball libsodium stable сначала отклонён; после проверки официальной minisign-подписи новый SHA-256 закреплён. Два upstream тестовых executable первоначально потеряли право исполнения в рабочем каталоге; после восстановления прав официальный набор повторён: 101 PASS. Ошибок криптографических проверок не было.

## Проверка собранных файлов

- Portable Windows ZIP и server ZIP: все записи прошли CRC; пустых EXE/DLL/JAR/ICO нет.
- AEGIS.exe: настоящий PE32+ x86_64, Windows GUI subsystem; ICO содержит 16, 24, 32, 48, 64, 128 и 256 px.
- AppImage: настоящий исполняемый ELF с SquashFS; извлечение прошло, встроенная Java 21.0.12.1 запустилась на сборочном Linux.
- Минимальные jlink runtime клиента и relay выполнили тот же отдельный процессный тест доставки без системной Java.
- JAR common-protocol/client-core/client-ui в Windows и Linux побайтно совпадают. Исходники common-protocol побайтно совпадают с 0.1.0.
- В relay classpath нет client-core, JavaFX, libsodium, Tink, Bouncy Castle или JNA.
- Shell/Python scripts прошли синтаксическую проверку. Установка на текущий хост не выполнялась; его firewall, Tor, systemd, DNS и загрузчик не менялись.

## Не выполнено — блокирующая приёмка для полноценного выпуска

Нет доступных чистых Windows 11, CachyOS и Debian 13 VPS с управлением reboot; не предоставлены адрес и доступ к действующему relay пользователя. Поэтому не проверены:

- Нативный запуск EXE без глобальной Java, Windows ACL/Job Object, SmartScreen, Firewall, ярлыки и отображение иконки Windows shell.
- Запуск AppImage без установленных Java/Tor в реальном KDE CachyOS, FUSE, XWayland и системные графические зависимости.
- Установка и повторная установка на чистом Debian 13, systemd/UFW/AppArmor, реальный bootstrap 100%, доступность onion извне, upgrade/rollback и полный reboot.
- Сквозная цепочка Windows → настоящий Tor → Debian relay → настоящий Tor → CachyOS, двусторонние сообщения и файлы, offline, TTL и перезапуск обоих клиентов.
- Отключение питания и восстановление профиля/БД после аппаратного сбоя.

Компиляция, локальные процессы и headless GUI не засчитываются вместо этих пунктов. Setup EXE не создавался; штатный Windows способ распространения — portable ZIP. Независимый аудит безопасности не проводился.

## Порядок оставшейся приёмки

1. На отдельном Debian 13 x64 установить сервер из ZIP, выполнить `sudo aegis-server doctor`, записать hostname, зарегистрировать аккаунты, перезагрузить VPS. Повторить doctor; проверить прежний onion, пользователей и очередь.
2. На чистой Windows 11 обычным пользователем распаковать ZIP и запустить AEGIS.exe. На чистой CachyOS разрешить выполнение AppImage и открыть его. Никакую глобальную Java/Tor не устанавливать.
3. Проверить loopback 19050/19051/19120, Tor 100%, регистрацию и вход после перезапуска. Добавить друг друга, сверить fingerprints, отправить сообщения в обе стороны и разрешённый архив.
4. Закрыть одного получателя, отправить сообщение, дождаться его входа; проверить начало TTL только после доставки. Проверить TTL без открытия, после перезапуска, дубликат и потерю соединения до ACK.
5. Остановить собственный Tor: клиент должен перейти offline без прямого TCP. Проверить закрытие только собственного дочернего Tor, двойной запуск, backup/restore и отсутствие секретов в логах.
6. Повторить регистрацию при closed, лимите пользователей и занятом нике. Выполнить серверный upgrade и rollback на резервной копии, затем reboot.
