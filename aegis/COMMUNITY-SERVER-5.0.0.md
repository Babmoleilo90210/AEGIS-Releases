# Отдельный сервер АЕГИС 5.0.0

Организации, полномочия, новости, мероприятия и общая библиотека обслуживаются отдельным `community-server`. Действующий production Relay не меняется. Сервер запускается оператором отдельно; установка клиента не открывает новый порт в интернете, не меняет torrc и не создаёт производственную организационную инфраструктуру самостоятельно.

## Первоначальная настройка

Соберите штатный Java-модуль:

```sh
./gradlew :community-server:installDist
```

Для первоначальной настройки подготовьте два **разных** открытых Ed25519 identity key администраторов: 44 байта DER/X.509 либо Base64 такого ключа. Независимо сверьте SHA-256 каждого ключа с его владельцем. Nickname не служит основанием административных полномочий. Закрытые identity keys и release-signing key этому серверу не передаются.

Каждый администратор отдельно подготавливает 32-байтовый TOTP seed и вводит его в свой доверенный аутентификатор. Параметры: RFC 6238, HMAC-SHA-256, восемь цифр, 30 секунд. Файлы seed должны быть доступны только владельцу. Передача и начальная настройка аутентификаторов выполняются вне публичного репозитория и релизных файлов. CLI не печатает seeds, коды, KEK или закрытый сервисный ключ.

```sh
build/install/community-server/bin/community-server --init /srv/aegis-community \
  --first-public /secure/admin-one.pub \
  --first-fingerprint VERIFIED_FIRST_SHA256 \
  --first-totp /secure/admin-one.seed \
  --second-public /secure/admin-two.pub \
  --second-fingerprint VERIFIED_SECOND_SHA256 \
  --second-totp /secure/admin-two.seed
```

Пути и `VERIFIED_*` заменяются проверенными локальными значениями. Нужен отсутствующий целевой каталог с существующим родителем без символических ссылок. Сначала создаётся защищённый staging-каталог; после успешного bootstrap весь каталог публикуется атомарным переименованием. Существующий каталог не перезаписывается. При прерывании неопубликованный staging остаётся закрытым для посторонних и не принимается за рабочую установку.

Создаются собственная сервисная Ed25519 key pair, независимый случайный 32-байтовый KEK вторых факторов и отдельная SQLite. На POSIX каталог имеет `0700`, сервисные ключи и KEK — `0600`; предусмотрен owner-only Windows ACL, который требует отдельной нативной проверки. TOTP seeds в базе зашифрованы KEK, а их исходные файлы в рабочий каталог не копируются. После переноса в аутентификаторы обращайтесь с исходными seed-файлами как с секретами администратора. Сервисный ключ, KEK и база не должны попадать в source ZIP, GitHub, диагностические отчёты или публичную резервную копию.

## Запуск и доверие

```sh
build/install/community-server/bin/community-server --inspect /srv/aegis-community
build/install/community-server/bin/community-server --serve /srv/aegis-community --port 38150
```

CLI показывает только открытый сервисный ключ Base64 и его SHA-256. Отпечаток независимо передаётся владельцам клиентов. При несовпадении public/private key, некорректном marker, доступных посторонним секретных файлах или неподтверждённом bootstrap запуск не продолжается.

Сервис слушает `127.0.0.1`, а не публичный интерфейс. Отдельная согласованная операторская конфигурация Tor может направлять onion service на этот loopback-порт. Например, следующий фрагмент является **примером**, а не автоматически применяемой конфигурацией:

```text
HiddenServiceDir /var/lib/tor/aegis-community
HiddenServicePort 80 127.0.0.1:38150
```

Не заменяйте этим фрагментом настройки действующего Relay. Изменение production-инфраструктуры требует разрешения владельца. Реальный созданный onion-адрес и проверенный сервисный ключ указываются в настройках клиента; выдуманный рабочий endpoint по умолчанию не задан. Производственный клиент использует `TorTransport`, SOCKS с доменным onion-адресом и проверку подписей. Прямой HTTP fallback не предусмотрен.

Loopback HTTP предназначен для соседнего Tor-процесса в доверенной операторской среде. Подписи сами по себе не шифруют тело HTTP; конфиденциальность сетевого пути обеспечивает правильно настроенный onion-транспорт. Полностью скомпрометированный сервер/ОС находится за пределами гарантируемой защиты.

## HTTP-контракт и ограничения

Единственный RPC endpoint: `POST /api/v1` с точными UTF-8 JSON-байтами `{ "action": ..., "data": ... }`. Подпись Ed25519 проверяется до интерпретации JSON. Запрос связывает сервисную identity, HTTP method/path, timestamp, 32-байтовый случайный nonce и SHA-256 точного тела. Timestamp допускает отклонение не более 60 секунд; nonce сохраняется в SQLite и не принимается повторно. Уровень, роль, галочка, должность или actor из клиентских полей не становятся основанием авторизации.

Ответ подписывается сервисным ключом и содержит `requestIdentity` и `requestSha256` внутри подписанного тела. Клиент проверяет одновременно сервисную подпись, nonce, собственную identity и соответствие исходному запросу. Это исключает замену ответа другим корректно подписанным ответом при совпадающем nonce. Решение обработчика и `authorizationEpoch` фиксируются согласованно. Операции агента выполняются вне внешней SQL-транзакции; сами сервисы повторно проверяют ACL и версии, а transport не выдаёт результат под чужой новой эпохой разрешений.

Действуют лимиты: тело/ответ 8 МиБ, глубина JSON 16, 8192 узла, отсутствие дублирующих ключей, строгая UTF-8 и проверка surrogate pairs. Разрешены большие, но ограниченные Base64-строки вложений. Сжатые запросы и transfer encoding не используются. Одновременно работают два HTTP worker, очередь ограничена 16 заданиями; есть таймаут запроса 20 секунд, ограничения заголовков, соединений, глобальной частоты и частоты identity. Они ограничивают потребление ресурсов и не являются обещанием защиты от любого DoS.

Закрытый и отсутствующий материал возвращают одинаковый безопасный отказ. Ошибки внутреннего SQL, файловые пути, ключи, пароли, токены и тела запроса не записываются в пользовательский HTTP-журнал. Сервисные рабочие identity допускаются только к выделенным `agent.worker.claim/complete/fail`, даже если дополнительная роль ошибочно даёт им доступ к обычному содержимому.

## Проверки и оставшаяся приёмка

`CommunityHttpServerTest` и `CommunityMainTest` используют настоящий loopback HTTP, Ed25519, SQLite, AES-GCM/TOTP и отдельный реально запущенный процесс CLI `--serve`; это не mock HTTP. Отдельный `CommunityIntegration500Test` использует production CommunityClient и TorTransport через ограниченную SOCKS5 **тестовую** loopback-переадресацию одного заданного onion-имени, реальные отдельные encrypted vaults и серверные сервисы.

Эти проверки не являются запуском Tor, доказательством отсутствия DNS/IP-утечек или нативной приёмкой Windows/CachyOS. Фактические XML, журналы и SHA исходников находятся в `docs/test-results/5.0.0-community-http/` и `docs/test-results/5.0.0-community-integration/`. Итоговый общий прогон и проверка точных релизных бинарников выполняются отдельно. Production-конфигурация, публикация Stable и release-signing key этими испытаниями не затрагиваются.
