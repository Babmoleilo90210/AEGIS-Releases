# Предложение развёртывания общей системы АЕГИС 5.0.0

Статус: подготовлено для отдельного согласования владельцем. Production Relay, VPS, DNS, Tor-конфигурация существующего сервера и Stable feed этим пакетом не изменены. Это конкретный сценарий установки двух работающих Java-модулей, а не утверждение о состоявшемся production-развёртывании. Без запущенного и доверенно настроенного центрального сервиса новые общие разделы клиента не получают данные; письма, личный архив, Взор и Глас сохраняют отдельную архитектуру.

## Предлагаемая схема

Один центральный процесс `community-server` обслуживает организации, авторизацию, подтверждения пользователей, публикации, события, общую библиотеку, файлы, журнал и координатор заданий. Он слушает только loopback `38150`; отдельный Tor onion service отображает виртуальный порт 80 на этот адрес. Стандартный клиент и worker обращаются к координатору только через Tor SOCKS, проверяют закреплённый Ed25519 ключ сервиса и подписанные точные сообщения. Обычный клиент не использует прямой HTTPS к центральному серверу.

Рабочий процесс `news-worker` запускается независимо от пользовательских компьютеров под другой системной учётной записью. Он получает ограниченное задание по своей служебной Ed25519 identity, собирает разрешённые публичные HTTPS-источники и обращается к разрешённой модели. Координатор повторно проверяет доказательства и полномочия перед публикацией. Worker не получает identity администратора, пароли, личные письма, архив, глобальные API secrets или доступ к центральной БД. Его API-операции ограничены claim/complete/fail. Наличие общих серверных классов в worker JAR не выдаёт ему серверных полномочий.

Публичные источники и внешняя модель видят сетевой адрес серверного узла, а не пользовательского клиента. Маршрут сбора публичных новостей не объявляется анонимным. Локальная модель доступна только через явно разрешённый loopback endpoint; закрытые библиотечные материалы не направляются внешним моделям. Первоначально агент отключён, источники не добавлены и бюджет не разрешает расход средств. Включение и критическая конфигурация проходят отдельную аутентификацию и подтверждение второго администратора.

## Пакеты и требования

- `AEGIS-5.0.0-community-server.zip` — центральный процесс, общие протоколы, минимальные SHA-256 закреплённые зависимости, launcher и шаблон systemd.
- `AEGIS-5.0.0-news-worker.zip` — рабочий узел, необходимые общие классы, тот же проверенный набор зависимостей и шаблон systemd.
- Исходники и соответствующий commit находятся в общем исходном пакете 5.0.0. В каждом серверном ZIP есть `SERVER-BUILD-PROVENANCE-5.0.0.json` и `SHA256SUMS`.

Нужна полноценная Java 21 с `java.base`, `java.sql`, `java.xml`, `java.desktop`, `java.net.http`, `jdk.httpserver` и `jdk.crypto.ec`, работающий Tor и отдельные защищённые каталоги. Поддержка произвольного урезанного JRE не заявляется. Java не включена в серверные ZIP. Первое развёртывание предлагается на выделенном Linux-хосте с systemd; Windows CLI и ACL требуют отдельной серверной приёмки. Это не подмена нативной проверки настольного клиента Windows 11 или CachyOS.

Зависимости: Gson 2.14.0, SQLite JDBC 3.53.4.0, SLF4J API/NOP 2.0.17. Пакет не содержит JavaFX, JUnit, клиентскую базу, ключи владельца релизов, ключи сервера, TOTP-seeds, KEK и credentials внешних моделей. Лицензии и сведения о происхождении находятся в `licenses/`.

## Воспроизводимая подготовка операторских пакетов

Запускать только после фиксации итогового commit и успешных тестов; рабочее дерево должно быть чистым:

```bash
python3 tools/package-community500.py \
  --jdk /path/to/verified-java21-jdk \
  --jar-dir build/local-java21 \
  --deps /path/to/verified-runtime-dependencies \
  --deps /path/to/verified-test-and-sqlite-dependencies \
  --out /path/outside/source-checkout
```

Скрипт не обращается к сети и не развёртывает сервис. Он проверяет SHA-256 зависимостей, точно сопоставляет исходники/ресурсы с Git HEAD, заново компилирует три модуля и сравнивает каждую запись class/resource с уже подготовленными JAR. Дополнительный class, чужой ресурс, опасный атрибут манифеста, неподходящий JDK, изменение source tree или неверный hash прерывают упаковку. Затем формируются детерминированные ZIP entries, контрольные суммы и provenance. Проверка классов не заменяет сеть, нагрузку или установку в целевой серверной системе.

## Первичная настройка двух администраторов

Действия ниже выполняет оператор после согласования развёртывания, не приложение на компьютере пользователя. Приватные identity keys администратора и release-signing key не передаются операторскому CLI.

1. Каждый из двух независимых администраторов экспортирует только свой существующий публичный Ed25519 ключ АЕГИС. Формат — канонический X.509, 44 байта, либо Base64 этого файла.
2. Отпечатки SHA-256 публичных ключей сравниваются по независимому каналу. Nickname не является основанием назначения.
3. Каждый администратор отдельно подготавливает 32-байтовый случайный TOTP seed и регистрирует его на собственном устройстве второго фактора. Параметры — HMAC-SHA256, 8 цифр, 30 секунд. Для совместимого authenticator используется `otpauth://totp/...?...&algorithm=SHA256&digits=8&period=30`; секрет нельзя публиковать, отправлять в Work или журналы.
4. Два различных seed-файла передаются на операторскую машину защищённым способом, с доступом только владельцу. CLI читает ровно 32 байта и отказывает при доступе группе/остальным. Seed не задаётся в командной строке.
5. Оператор запускает подготовку нового, ещё не существующего каталога. Используются файлы и независимо проверенные отпечатки, а не вымышленные значения:

```bash
/opt/aegis-community/bin/community-server --init /var/lib/aegis-community \
  --first-public /secure/bootstrap/first-public.x509 \
  --first-fingerprint FIRST_VERIFIED_SHA256 \
  --first-totp /secure/bootstrap/first-totp.bin \
  --second-public /secure/bootstrap/second-public.x509 \
  --second-fingerprint SECOND_VERIFIED_SHA256 \
  --second-totp /secure/bootstrap/second-totp.bin
```

CLI создаёт отдельную служебную Ed25519 пару, отдельный 32-байтовый KEK, SQLite и завершённый bootstrap в частном временном каталоге, затем атомарно переносит каталог на назначенное место. Два начальных администратора не создают пользовательские роли автоматически. Обычные пользователи, которым нужны управление организацией или делегированные роли, подключают собственный первый TOTP через настройки безопасности приложения. Эта операция запрещена для существующего фактора и не заменяет процедуру сброса двумя администраторами. TOTP-seeds сохраняются в SQLite только под AES-GCM. Приватные ключи сервера и KEK остаются в его защищённом каталоге. Не включайте этот каталог в Git, diagnostics или публичный release.

```bash
/opt/aegis-community/bin/community-server --inspect /var/lib/aegis-community
/opt/aegis-community/bin/community-server --serve /var/lib/aegis-community --port 38150
```

`--inspect` выводит только открытый ключ сервиса и его SHA-256. Открытый ключ и onion-адрес администратор передаёт пользователям по доверенному каналу. Клиент настраивается в разделе сети/общей системы; ключ нельзя автоматически подменять данными из неподписанного каталога.

Инициализацию выполняйте под той отдельной системной учётной записью, которая впоследствии запускает сервис, либо явно назначьте владельца частного каталога в соответствии с локальной политикой. Не запускайте всё настольное приложение от root/администратора. Шаблон `aegis-community.service` задаёт отдельного пользователя, минимальные возможности, закрытый home, ограниченные ресурсы и разрешённый каталог записи. Его установка и включение не выполняются автоматически.

## Предложение Tor-конфигурации

Используется новый каталог onion service, не каталог существующего почтового Relay:

```text
HiddenServiceDir /var/lib/tor/aegis-community/
HiddenServicePort 80 127.0.0.1:38150
```

Эти строки должен проверить и применить оператор Tor после отдельного разрешения владельца. Имя службы и права Tor-каталога зависят от конкретной ОС. Центральный Java-сервис должен слушать именно IPv4 loopback, соответствующий этому отображению. Адрес берётся из `hostname` нового onion-каталога; остальные файлы являются секретами onion service и не включаются в клиентский пакет. Открывать `38150` наружу не требуется. Не меняйте существующий Relay onion service и его ключи.

Синтаксис и значение HiddenServiceDir/HiddenServicePort сверены с официальной инструкцией Tor Project: https://community.torproject.org/onion-services/setup/ (проверено 15.10.2026). Официальная инструкция также рекомендует Unix socket там, где он поддерживается; текущий Java HttpServer использует проверенный loopback TCP и не заявляет реализацию Unix socket listener.

## Настройка worker

Worker генерирует собственную служебную пару в новом защищённом каталоге:

```bash
/opt/aegis-news/bin/news-worker --generate-key /etc/aegis/worker-identity
```

Рабочий ключ не должен принадлежать обычному пользователю или администратору АЕГИС. Сначала необходимо зарегистрировать его публичную identity в центральной системе: с правильным onion-адресом, закреплённым ключом сервиса и доступным Tor выполнить приведённый ниже запуск `--once` **до** назначения роли. Первый подписанный `agent.worker.claim` регистрирует identity отдельной завершённой транзакцией, но сам claim закономерно отклоняется из-за отсутствия полномочий. Это не успешное получение задания. CLI выводит общее сообщение о недоступности; его exit code сам по себе не отличает отказ от сетевой ошибки и не доказывает регистрацию.

```bash
/opt/aegis-news/bin/news-worker \
  --server http://VERIFIED_56_CHARACTER_SERVICE.onion \
  --server-key VERIFIED_SERVICE_PUBLIC_KEY_BASE64 \
  --worker-key /etc/aegis/worker-identity/worker.pk8 \
  --tor-socks 9050 --once
```

После первого подписанного обращения два администратора с действующим TOTP создают минимальную глобальную роль только с `AGENT_WORK`, согласуют её назначение точному fingerprint worker и регистрируют эту же identity в координаторе. Используются независимые критические заявки для создания роли, её назначения и включения узла. Worker не вступает в организации и не получает другие роли. Если назначение отклоняется из-за отсутствующей identity, проверить onion/Tor/закреплённый ключ и повторить первый запуск. Затем повторить `--once`: теперь разрешённый claim принимается; при выключенном агенте или отсутствии заданий допустим ответ без задания. Разрешения администратора, модерации, чтения закрытой библиотеки и самостоятельной глобальной публикации worker не выдаются. HTTP-граница дополнительно ограничивает зарегистрированный worker операциями claim/complete/fail.

Этот порядок проверен отдельно с финальными production-классами WorkerCoordinatorClient, CommunityHttpServer, Ed25519 и настоящей временной SQLite: отказ первого claim сохраняет identity, видимую из независимого подключения; реальные двухадминистраторские операции позволяют второй claim; identity сохраняется после открытия БД заново. Тест использовал loopback connector seam и не является испытанием Tor или развёрнутого сервиса. Временная БД удалена, её данные и ключи не входят в комплект.

`--once` — однократное операторское испытание доступного задания. После проверки можно запустить тот же узел без `--once`, под отдельной службой. Приведённые значения адреса и ключа — обозначения полей, их нельзя выдавать за действующую production-конфигурацию. Файл `news-worker.env` при использовании шаблона systemd создаётся оператором с минимальными правами. Он не входит в пакет. Для внешнего провайдера задаются только разрешённые `AEGIS_NEWS_API_KEY_...` environment credentials рабочего процесса; их содержимое не передаётся другим организациям или диагностике.

Текущая модель выбирается администрацией и отдельно устанавливается/разрешается на сервере. Платный API не нужен для существующих писем, архива и звонков. Без разрешённой модели/источников агент должен оставаться остановленным, а не создавать выдуманные публикации. Локальные fixture-тесты API и RSS не доказывают качество реальной модели или источника.

## Издатель, модель и секреты центральной проверки

До включения агента подготовить отдельный аккаунт издателя и один раз подключить его клиент к выбранному Community-сервису, чтобы зарегистрировать существующий публичный ключ. Два администратора назначают этой identity минимальные глобальные `NEWS_CREATE` и `NEWS_PUBLISH`. `NEWS_GLOBAL_PUBLISH` выдаётся только при явно разрешённой всеобщей публикации. Издателю не выдаётся `AGENT_WORK`; его приватный identity key не передаётся worker или центральному CLI. В конфигурации агента указывается точный fingerprint издателя, а не nickname.

Администрация регистрирует нормализованные города, законно доступные источники и независимые группы источников, выбирает модель и endpoint, задаёт верхние тарифы и лимиты запросов/токенов/денег, затем включает агент. Критическая конфигурация подтверждается вторым администратором. Без модели, источников, бюджета и прав издателя агент не считается готовым к публикации.

Для внешнего провайдера конфигурация содержит только имя переменной, например `AEGIS_NEWS_API_KEY_MAIN`. Фактическое значение необходимо в защищённом окружении **обоих** процессов: worker выполняет исходный анализ, а центральная служба отдельно формирует и проверяет редакционный результат. Можно использовать отдельный ограниченный ключ провайдера для каждого процесса, сохранив одинаковое имя переменной из `credentialRef`. Один лишь секрет worker не включает центральную проверку.

Для центральной службы оператор создаёт закрытый root-owned файл `/etc/aegis/community-model.env` (0600) и drop-in через `systemctl edit aegis-community.service`:

```ini
[Service]
EnvironmentFile=/etc/aegis/community-model.env
```

Значение выбранной переменной `AEGIS_NEWS_API_KEY_...` записывается только в закрытый файл. Секрет нельзя добавлять в командную строку, Git, release или diagnostics. Worker использует предусмотренный `/etc/aegis/news-worker.env` с закрытыми правами. После изменения unit/drop-in оператор выполняет `systemctl daemon-reload` и контролируемо перезапускает соответствующую службу. Нужны также собственные лимиты расходов у провайдера. Эти команды и развёртывание автоматически не выполнялись.

При Ollama модель должна быть установлена и доступна на разрешённом literal-loopback endpoint каждого хоста, выполняющего анализ: центрального и worker. Если процессы находятся на одном хосте, возможен один согласованный локальный экземпляр с разными системными пользователями. АЕГИС не загружает модель автоматически; localhost другого хоста не превращается в удалённый endpoint.

## Данные, резервные копии и восстановление

Центральная SQLite содержит общие материалы с серверным ACL, а не личный архив. Защищённые резервные копии включают согласованную БД, служебную key pair, KEK и onion keys. Хранить их нужно раздельно от публичного release, с контролем доступа и подтверждённой процедурой восстановления. Копирование работающего SQLite одним несогласованным файловым чтением не является проверенной резервной копией; для операторской копии сначала остановите сервис либо используйте согласованный SQLite backup.

Аудит связан hashchain и HMAC от отдельного KEK; изменение записей без KEK обнаруживается. Без внешнего якоря целиком откатанная БД или усечённый корректный хвост журнала не гарантированно обнаруживаются. Полная компрометация сервера вместе с его секретами также выходит за пределы этой меры. Нужны внешние контрольные точки и операторский мониторинг; они не выдаются за выполненную production-функцию.

Откат центрального бинарника допускается только вместе с проверкой совместимости его схемы. Серверная 5.0.0 БД не является базой почтового Relay 2.5.0. Нельзя открывать её старым Relay или смешивать каталоги. Перед миграцией/откатом использовать отдельную согласованную копию. Восстановление административного доступа не должно незаметно обходить два независимых подтверждения; автоматического аварийного master-password нет.

## Приёмка перед подключением пользователей

Проверить в отдельной среде: bootstrap двух identity, серверный второй фактор, отдельное подтверждение критической операции, отклонение self-approval/replay/неверного ключа, недоступность HTTP порта извне, настоящий onion-маршрут, отказ прямого подключения клиента, создание/одобрение организации, роли и отзыв, скрытый документ через API/поиск/граф/экспорт, worker без административного доступа, реальные разрешённые источники и модель, бюджеты и остановку агента, региональные ленты, события и регистрацию, перезапуск с сохранением данных, резервную копию и восстановление.

До production-подключения нужны отдельное разрешение владельца, наблюдаемые результаты сетевой/нагрузочной приёмки, проверка серверной ОС и актуальных зависимостей, финальные desktop native acceptance и updater E2E. Успешные JUnit/локальный HttpServer не заменяют эти испытания. `productionReady` остаётся `false`, пока обязательные условия не подтверждены для точных готовых артефактов.
