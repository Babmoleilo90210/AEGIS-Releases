# Переход с 0.3.0 на 1.0.0

Обновляются только клиенты. Relay 0.2.0, protocol 1, его БД, onion identity, Tor и регистрация не меняются. Новый аккаунт не создаётся.

## Данные

Перед открытием старого vault создаётся `backups/pre-1.0.0-<timestamp>-<uuid>/`: полный зашифрованный каталог vault, настройки, тема, сохранённый Tor mode и путь исходного профиля. State включает идентичность, контакты, dedup/ACK; папки mail/sent содержат ciphertext писем. Установка Windows дополнительно делает snapshot даже перед повторной установкой нового формата. Локальные пароли в backup не записываются.

Существующие настройки определяют реальный storagePath, включая старую CachyOS `~/.local/share/aegis`. Данные не переносятся в другой пустой профиль. Сохранённый .onion не переписывается.

Сначала клиент пробует пароль аккаунта для старого vault. При несовпадении показывает одно окно «Обновление хранилища → Старый пароль хранилища». Неверный ввод можно повторить; оригинал и snapshot сохраняются. Правильность пароля аккаунта затем проверяет действующий relay с той же идентичностью. До успешной авторизации ключ vault не меняется.

Клиент создаёт соседний staging-каталог и перешифровывает **state, все входящие и отправленные файлы**, с новыми солью/nonce и отдельным контекстом Argon2id `AEGIS-VAULT-v1`. Внутренние signed packets, ACK digest и сроки TTL сохраняются. В staging нет файлов с расшифрованным приватным ключом или текстом письма.

Новая копия открывается новым паролем и проверяется: идентичность, nickname, contacts, dedup и каждый пакет. Только затем закрываются файловые handles старого vault и выполняются directory rename. Journal находится рядом с vault; при незавершённом commit следующий запуск восстанавливает предыдущий каталог. Предыдущая зашифрованная папка `.pre-migration-*` и dated backup сохраняются. Ошибка не запускает новый пустой LocalStore.

State/mail container остаётся v1. Файл `vault-kdf` фиксирует новый KDF context. Старый vault без marker использует прежний Argon2id; неизвестный marker отклоняется. Identity export AEB2 включает признак нового KDF; импорт AEB1 0.3/0.2 тоже поддерживается. После восстановления AEB1 при входе выполняется та же миграция.

## Программа и откат

Windows Setup закрывает окно Java только если полный путь процесса совпадает с runtime прежней установки. Её launcher Job Object завершает собственные Tor/PT. Затем новый встроенный runtime создаёт backup без доступа к паролям. Прежняя папка программы переименовывается в `AEGIS.rollback-1.0.0`, новые файлы устанавливаются на прежнее место, обновляются HKCU и ярлыки. При ошибке копирования возвращается прежняя программа. При технической ошибке миграции установленный клиент запускает отдельный локальный helper для отката программы после завершения своего Java и launcher; только этот helper явно выходит из Job Object, Tor/PT остаются его обычными дочерними процессами; данные остаются прежними. Ошибка пользовательского пароля не запускает откат программы: ввод можно повторить. Native Windows-проверка этого механизма ещё обязательна.

CachyOS обновляет образ **после** успешного входа и миграции. Подтверждённый старый процесс закрывается по APPIMAGE-пути; заранее закреплённые pidfd дочерних процессов используются для остановки. pidfd предотвращает отправку сигнала новому процессу при повторном использовании PID; NSpid учитывает namespace. При недоступном pidfd обновление останавливается и сохраняет старые данные. Стабильный образ заменяется через same-filesystem atomic rename, прежний сохраняется как `AEGIS.pre-1.0.0.AppImage`. При ошибке установки восстанавливаются образ, desktop entry и иконка. User data не удаляются. Существующая 0.3 не умеет открывать новый KDF: для возврата программы после успешной миграции нужен также старый зашифрованный backup.

TTL остаётся действующим: просроченные файлы удаляются при запуске/открытом клиенте; migration не продлевает deadlines. Резервные копии содержат ciphertext и могут сохранять уже истёкшие пакеты; TTL не контролирует пользовательские backup/экспорты.

## Совместимость и ограничения

1.0 читает client content v1 и v3, создаёт v4 для нескольких вложений. Relay видит прежний opaque ciphertext. Старый клиент 0.3 не понимает v4; получателям новых писем нужна 1.0.

Protocol 1 передаёт прежний пароль аккаунта внутри Tor-соединения для серверного Argon2id. Изменение wire authentication material сломало бы существующие аккаунты, поэтому client AUTH context на сети не вводится. Vault key выводится отдельно, со своей случайной солью и context, и никогда не отправляется серверу. Один ввод пароля не означает один raw cryptographic key. При захвате работающего relay пароль аккаунта может быть перехвачен; тот же пароль позволит открыть украденный vault. Domain separation не защищает от знания исходного пароля. Это ограничение описано в SECURITY.md.

Реальный тест: профиль создан **выпущенными 0.3.0 JAR/runtime**, зарегистрирован на **выпущенном relay 0.2.0**. Проверены отдельный старый пароль, 11 контактов, inbox/sent, старое вложение, onion, snapshot, отказ при неверном пароле аккаунта, последующий вход одним паролем. SOCKS routing в этом тесте локальный; Windows/CachyOS acceptance по настоящей сети требуется отдельно.
