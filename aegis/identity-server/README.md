# Identity АЕГИС 6.0.0

Реальная отдельная служба идентичности на JDK 21 / SQLite. В ней нет ключей расшифрования Почты, архива или release-signing key. Клиенты обращаются к `/identity/v1` через отдельный Tor onion service. Сервер слушает только loopback. `IdentityHttpServerTest` использует HTTP на loopback как локальный интеграционный стенд; этот тест не является проверкой Tor.

## Ключи и полномочия

Постоянный `accountId` — SHA-256 канонического 44-байтового X509 Ed25519 public key прежней identity. Корневой private key остаётся в Почте; новый сервер получает только public key и подписи строго типизированных операций. Device, recovery и каждое приложение используют разные Ed25519 ключи. Сервер отклоняет смешение этих ключей и использование одного app key разными приложениями или устройствами. При смене app key старые capabilities этого приложения отзываются.

Первая регистрация требует подписи account root и нового device над одной регистрацией, включающей отдельный recovery public key. Повторная регистрация не сбрасывает аккаунт. Следующее устройство получает одноразовое одобрение активного доверенного устройства после повторной аутентификации либо подтверждение двумя ключами account root + recovery. Восстановление отзывает прежние устройства/сессию и ставит флаг дополнительного рассмотрения чувствительных полномочий; снятие флага требует отдельного двухстороннего административного review (`sensitiveRecoveryApprove`). Реализована атомарная передача владения с четырьмя root/device proofs и действующим двухсторонним critical permit. Восстановление владельца использует root+recovery и последующее рассмотрение двумя другими ADMIN; при потере quorum оно блокируется. Полный контракт и fixed Mail consent — в OWNER-ADMINISTRATION-6.0.0.md.

Успешный вход увеличивает generation в `BEGIN IMMEDIATE`, связывает её с **конкретным active device**, отзывает все прежние tokens и step-up. Даже старое доверенное устройство, узнав номер новой generation, не может выпустить capability. Повторный вход с двух соединений проверен гонкой: остаётся одно поколение/устройство. Старые Relay/Community 5.0 не используют этот gate автоматически — совместимость с ними и принудительное применение общей сессии требуют отдельной интеграции, это не объявлено выполненным.

Capabilities подписаны отдельным ключом сервиса, содержат account/device/app/generation/audience/tokenId, app proof key, права, issued/expires/offlineUntil. Предельная жизнь — 24 часа. Каждая операция дополнительно подтверждается app proof-of-possession над точным типизированным action, SHA-256 фактических байтов операции, nonce и временем. Нельзя передать одну подпись от чтения как право изменения. Приёмник самостоятельно считает digest; доверять присланному клиентом digest без сравнения с операцией запрещено.

`isActive` возвращает только boolean, проверяет подпись, точный persisted token, generation, active device и срок. Для ADMIN он также повторно проверяет актуальное административное право, свежий step-up и отсутствие ограничения восстановления. Для восстановленного аккаунта до административного review консервативно запрещены **все** операции Библиотеки, включая публичные; issue/authorize/isActive применяют этот запрет. Он используется **после** проверки app proof, а не вместо неё. При ошибке сети получатель отказывает. Повторные проверки во время передачи ограничены политикой конкретной службы; если служба кэширует результат на 250 мс, это ограниченная задержка отзыва, а не мгновенный отзыв.

`OfflineLeaseGuard` использует подписанное время, wall time, монотонный elapsed clock и сохранённую верхнюю границу wall time, привязанную к tokenId в зашифрованном состоянии клиента. Он всегда отказывает закрытым материалам офлайн. При перезапуске elapsed clock создаётся новый anchor только после онлайн-аутентификации. Одновременное восстановление старого диска и откат ОС-часов без доверенных аппаратных часов полностью не предотвращаются. Уже полученные офлайн-копии невозможно гарантированно стереть удалённо.

## Реальный Owner Bootstrap

Сначала собрать `:identity-server:installDist`, установить комплект в приватный служебный каталог и указать JDK 21. Создание собственного service key/audit key не использует ключи владельца:

```sh
bin/aegis-admin init --home /var/lib/aegis-identity
bin/aegis-admin serve --home /var/lib/aegis-identity --port 19120
```

Домашний каталог службы имеет права 0700, ключи/SQLite/WAL/SHM — 0600. `service-public.txt` содержит публичный ключ для независимой сверки/pinning клиента. Пользователи должны доверенно сверить fingerprint перед первой регистрацией. Tor endpoint настраивается отдельно оператором в staging, production автоматически не изменяется.

Аккаунт уже должен быть зарегистрирован с валидным root/device proof. Затем на сервере:

```sh
bin/aegis-admin owner bootstrap --home /var/lib/aegis-identity \
  --account-id ACCOUNT_ID --challenge /private-transfer/owner-challenge.json
```

Публичный challenge содержит audience/accountId/nonce/expiry и точные `proofBytes`. Почта после явной повторной аутентификации должна **восстановить `IdentityProtocol.ownerBootstrap(...)` из полей**, проверить сервис, account ID, срок и равенство байтов и подписать именно этот тип операции. Нельзя предоставлять общий IPC «подпиши произвольные байты». CLI не принимает root private key и не запрашивает экспорт расшифрованного ключа.

Ответ владельца — JSON с ровно `audience`, `accountId`, `challenge`, `signature` (base64url без `=`). Затем:

```sh
bin/aegis-admin owner bootstrap --home /var/lib/aegis-identity \
  --account-id ACCOUNT_ID --proof /private-transfer/owner-proof.json
bin/aegis-admin inspect --home /var/lib/aegis-identity
```

Одноразовый singleton назначается атомарно. Другой ключ, сервис, аккаунт, истёкший challenge, повторное назначение и конкурентное второе назначение отклоняются. Сам CLI не даёт пользователю возможности подписать доказательство; клиентская типизированная выдача proof — отдельная интеграционная задача. Секреты не выводятся в журнал.

## Первый делегированный администратор

Изначально системных ролей ровно две: «Владелец АЕГИС» и «Обычный пользователь». Официальная галочка владельца независима от любых других подтверждений и уровней. Первая дополнительная административная роль имеет **имя, введённое владельцем**, а не готовую встроенную роль.

Обычное требование двух действующих администраторов не может само создать первого делегата. Для этого реализована отдельная, явно одобренная в рамках ТЗ 6.0 процедура:

1. Владелец с активной ADMIN capability и свежим root/device step-up выбирает **другой существующий аккаунт** и имя роли. `firstDelegateChallenge` проверяет, что делегированных администраторов ещё нет и вечный флаг первого назначения не использован.
2. Выдаётся challenge на 120 секунд, связанный с сервисом, обоими account ID, обоими текущими device ID/generation и именем роли.
3. Оба участника проверяют поля и явно подтверждают именно `IdentityProtocol.firstDelegateConsent(...)`. Требуются **четыре подписи**: root и device владельца, root и device выбранного участника.
4. `firstDelegateComplete` повторно проверяет текущие сессии, step-up владельца, все подписи и срок в одной SQL-транзакции. Создаётся именованное делегированное ADMIN-полномочие, выставляется вечный `first_delegate_used=1`, журнал содержит подтверждения обоих участников.
5. Отзыв всех делегатов не сбрасывает этот флаг. Повторное использование первой процедуры запрещено. Отдельное аварийное восстановление здесь не подменяется скрытым обходом.

Чужое root/device proof, изменённое имя роли, смена любого поколения, self-confirmation, expiry, replay и конкурентные завершения проверены тестами. После первого назначения все последующие назначения/отзывы администраторов требуют обычного двухстороннего critical permit.

## Критические операции

`requestCritical` фиксирует operation, точные payload bytes, инициатора, его capability и expiry. `approveCritical` требует другую действующую ADMIN identity и свежую повторную аутентификацию. `consumeCritical` повторно проверяет обе стороны, полномочия, текущие generations, подписи, payload и одноразовость. SQL выполняет проверку/изменение атомарно. `sensitiveRecoveryApprove` снимает ограничение восстановления только после двухстороннего permit для точного account ID и отзывает прежние tokens/step-up этого аккаунта. `administratorAssign` и `administratorRevoke` принимают только такие permits; нельзя назначить владельца или отозвать его через этот API.

Служба Management может применять собственный эквивалентный двухсторонний proof к тем же exact operation bytes, если она повторно проверяет обе ADMIN capabilities, срок, generation и одноразовость непосредственно перед действием. Одна ADMIN capability сама по себе не является двухсторонним подтверждением опасного действия.

**Выпуск программ исключён из требования второго администратора.** `ownerReleaseApproval` требует именно владельца и записывает одобрение digest. Он не публикует GitHub Release, не подписывает manifest ключом владельца и не меняет update feed.

`AdministrativeAuthority` — узкий серверный callback для будущего доверенного источника глобальных ролей. По умолчанию он всегда запрещает. Признаки клиента, nickname, обычная галочка и старые Community роли не признаются административными автоматически. Полный конструктор глобальных/организационных allow/deny-ролей остаётся в Community; его доверенное соединение с Identity — отдельный gate, а реализованный именованный ADMIN-делегат не выдаётся за весь конструктор.

## Ограничения и испытания

RPC: точные ключи JSON, максимум 64 KiB/512 nodes/12 вложений; запрещены дубли, дробные/переполненные числа, плохой UTF-8 и lone surrogate. Два worker, очередь 16, timeout 15 секунд; общий ingress 6000/min, control 600/min, boolean recheck 4000/min. SQL nonces ограничены 20000, tokens — 128/account, devices — 32/account, pending challenges — 32/account, pending critical — 256, accounts — 10000. Достижение лимита прекращает операцию.

Audit — цепочка SHA-256/HMAC-SHA256 с отдельным случайным 32-байтовым ключом и текущим head/seq в metadata. Изменение строки и усечение хвоста без согласованного отката обнаруживаются. Откат **всего** старого SQLite вместе с metadata не обнаруживается без независимого внешнего checkpoint; такой checkpoint здесь не заявлен. Компрометация VPS, включая ключ аудита, остаётся общей границей доверия.

Локальный воспроизводимый запуск без загрузок:

```sh
python3 identity-server/tools/test-local.py --jdk VERIFIED_JDK_21 \
  --deps REVIEWED_MAVEN_JARS --deps JUNIT_CONSOLE_JARS --out /tmp/identity-test
```

Основная сборка: `:identity-server:test :identity-server:installDist`. Общий кодек дополнительно компилируется `javac --release 8`; Android API 33 предоставляет Ed25519 JCA. Локальные тесты используют реальные JCA/SQLite/HTTP, а не Tor/Android/Windows/физические устройства. Эти платформенные проверки и packaged end-to-end Mail/Core workflow не считаются автоматически пройденными. Типизированные Bootstrap/FirstDelegate/OwnerTransfer протоколы, Mail broker и серверные проверки реализованы; нативная и Tor приёмка фиксируются отдельно.
