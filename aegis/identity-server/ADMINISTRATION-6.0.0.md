# Управление полномочиями Identity 6.0.0

Встроенная панель Core выполняет три операции Identity: назначение администратора с выбранным названием должности, отзыв полномочий и снятие ограничения чувствительного доступа после восстановления устройства. Это серверные операции; изменение клиентских данных не выдаёт права.

## Подтверждение

1. Действующий администратор проходит повторную аутентификацию в независимой Почте и создаёт ограниченный по сроку запрос.
2. Второй действующий администратор получает публичный JSON-код, сверяет полные account ID и действие, повторно подтверждает личность в Почте и одобряет запрос.
3. Инициатор повторно аутентифицируется и выполняет ту же операцию.

Каждый шаг проверяется Identity. Публичный код связывает audience сервиса, инициатора, назначение операции, целевой account ID, название должности, request ID, SHA-256 канонического payload и срок действия. Он не содержит приватных ключей, паролей или токенов сессии. Парсер отклоняет неизвестные и повторяющиеся поля, неверные типы и несовпадение payload. Код действует не более пяти минут; действительность step-up дополнительно ограничивает выполнение.

Перед одобрением и выполнением Core вызывает `criticalInspect`. Этот запрос использует отдельный домен `AEGIS-IDENTITY-CRITICAL-INSPECTION/v1`, действующую ADMIN capability и свежий proof of possession приложения. Подписанный ответ содержит метаданные сохранённого сервером запроса. Core сравнивает все поля со своим публичным кодом. Inspection самостоятельно ничего не изменяет и не подтверждает.

Сервер повторно проверяет обе административные capability, поколения устройств, действующие полномочия и step-up непосредственно при потреблении одноразового разрешения. Смена сессии инициатора или подтверждающего администратора делает прежний запрос недействительным.

## Кворум и отзыв

При отзыве целевой пользователь не может быть инициатором или вторым подтверждающим администратором. Это сохраняет двух не затронутых отзывом администраторов. При передаче статуса владельца получатель не может одновременно быть вторым административным подтверждающим: после передачи прежний владелец становится обычным пользователем.

Отзыв записывает постоянный `revoked_admin_user` marker в SQLite, отключает делегированную роль и удаляет старые capability пользователя. Marker запрещает повторное получение административных прав через прежний внешний `AdministrativeAuthority`, в том числе после перезапуска. Он снимается только успешным назначением, прошедшим процедуру двух администраторов. История аудита при этом сохраняется.

## Восстановление устройства

Фиксированное подтверждение root identity и отдельного recovery key позволяет привязать новое устройство. Оно отзывает прежние устройства и сессии, но оставляет `sensitiveRecoveryPending=true`. До независимого административного рассмотрения защищённая библиотека и ADMIN capability недоступны. Два других действующих администратора снимают ограничение через `APPROVE_RECOVERY`; эта операция не выдаёт административную роль. Приватные root/recovery ключи остаются в Почте.

## Проверка восстановленного кода

Локально выполнены 82 теста Identity и пять тестов Core administration flow: реальные SQLite, Ed25519, подписанный HTTP, операторский bootstrap и проверки одноразовых разрешений. Все 87 завершились успешно, пропущенных нет. Запись результатов: `docs/test-results/6.0.0/identity-restored/RESULT.json`; тестовый runner и точные SHA-256 исходников сохранены рядом. В подкаталоге `ui` сохранена отдельная настоящая JavaFX-проверка панели и два снимка экрана.

Эти испытания используют отдельные тестовые ключи и loopback-транспорт. Они не являются нативной приёмкой Windows/CachyOS/Debian, испытанием реального Tor или подтверждением независимого окна Почты. Итоговая готовность релиза определяется общей матрицей приёмки.
