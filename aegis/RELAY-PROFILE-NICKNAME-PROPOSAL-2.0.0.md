# Отдельное согласование Relay: профили и изменение nickname

Статус: предложение владельцу, не разрешение на изменение production. Ни развертывание Relay, ни новый wire opcode этим документом не выполняются.

## Публичные профили и аватары

В исходниках уже есть signed `PublicProfile` и capability bit 1 действующего protocol 1. Если используемый сервер возвращает capability 0, требуется развернуть совместимую реализацию существующих операций profile-get/profile-publish. Изменение криптографического формата для доставки аватаров не требуется. Проверку фактического production capability и развертывание выполнять только после отдельного разрешения.

Сначала поднять отдельный staging Relay с временной БД и отдельным onion. На нём проверить два обычных тестовых аккаунта через настоящий Tor: A публикует нормализованный PNG, B получает подписанный профиль; A меняет/удаляет аватар и скрывает профиль, B получает более новую revision после синхронизации. Проверять владельца identity, подпись, anti-replay, совпадение nickname/userId/publicKey, ограничение размера PublicProfile и отсутствие приватных данных в ответах и журналах. Не менять production Stable feed или release key.

При `visible=false` сервер хранит и отдаёт подписанную пустую версию: пустые about и avatar. Старые локальные копии у офлайн-получателя невозможно отозвать удалённо; интерфейс обязан обозначать сохранённую версию. После получения скрытой более новой версии B удаляет отображаемый аватар. Удалённые изображения не подменяются изображением локального пользователя.

## Почему nickname пока нельзя менять только в клиенте

Текущий nickname является уникальным регистрационным именем и индексом каталога Relay. `LocalStore.bindNickname` защищает его от случайной подмены. У сервера нет операции rename. Локальная правка без поддержки сервера нарушила бы вход, поиск контактов и проверку подписанных профилей. Генерация новой identity не является переименованием.

## Требуемая серверная операция

Предлагается отдельная capability для rename, выделенная после проверки свободных битов protocol. Конкретный opcode и формат следует утвердить с владельцем до реализации. Запрос должен включать текущую аутентифицированную сессию, неизменный userId, старый nickname, новый nickname, уникальный requestId, revision и подпись текущим identity key. Новое имя проходит действующую `Limits.nickname`, проверку уникальности и атомарный контроль последней revision. Повторение requestId с тем же содержимым возвращает прежний результат; конфликтующее содержимое отклоняется.

Одна транзакция SQLite проверяет права сессии и уникальность, меняет каталог account name и сохраняет подписанное соответствие старого/нового имени неизменному userId/publicKey. Пароль аккаунта, password verifier, identity keys, письма, receipts, исчезающие письма, доверие контактов и содержимое архива не пересоздаются. Старое имя резервируется за прежним userId либо становится проверяемым alias согласно отдельно утверждённой политике. Молчаливое немедленное переиспользование старого имени другим человеком недопустимо.

Клиент получает подписанный результат и обновляет nickname только после подтверждённого серверного commit. Обновление выполняется с зашифрованным snapshot профиля и recoverable journal. Контакты по-прежнему закреплены за userId/publicKey; обновлённое отображаемое имя принимается только по подписанному соответствию. Исторические пакеты и их подписи не переписываются. Аватар-кэш адресуется userId; AAD и локальные индексы, содержащие старый nickname, мигрируются атомарно либо сохраняются как исторические ссылки.

## Приёмка до production

Проверить конкурентный rename двух аккаунтов на одно имя, повтор запроса после разрыва Tor, истёкшую/чужую сессию, поддельную подпись, replay revision, Unicode/недопустимые символы, лимиты и rate limiting. Проверить вход старым/новым именем согласно утверждённой политике aliases, доставку старых и новых писем, сохранность ключей и архива, обновление контакта вторым пользователем, rollback при сбое локального commit. Staging evidence и план восстановления БД представить владельцу до разрешения production deployment.

До отдельного согласования и реализации этой операции поле nickname остаётся явно read-only. Поэтому требование ТЗ 2.0.0 о редактировании nickname ещё не выполнено и не должно попадать в PASS.

## Конкретный вариант для согласования

Проверены действующие `Operation`: заняты1–15; сервер объявляет bits1(profile) и2(contacts). Важная совместимость: клиент1.5 отвергает неизвестные capability bits (`value & ~3`). Поэтому **не добавлять bit4 в существующий ответ11** — это сломает старых клиентов.

Предлагается, без изменения существующего wire:

| Предлагаемый новый opcode | Назначение |
|---|---|
|16 CAPABILITIES_V2|Версионированный расширенный ответ; старый Relay возвращает действующий error1, новый клиент сохраняет legacy capabilities|
|17 NICKNAME_RENAME|Аутентифицированная атомарная смена канонического nickname неизменного userId|
|18 NICKNAME_BINDING_GET|Получение owner-signed цепочки имён/canonical binding с проверкой закреплённого identity key|

Это **предлагаемые**, ещё не реализованные значения. Ответ CAPABILITIES(11) остаётся прежним0/1/2/3. Новая capability rename находится только в версии ответа16. Никакой существующий opcode/формат PublicProfile/письма не переписывается.

Предлагаемая политика aliases: прежнее имя навсегда резервируется за тем же userId и больше не выдаётся другому аккаунту. Старое и новое имена принимаются для входа в тот же аккаунт; пароль/verifier и identity keys не меняются. Legacy FIND старого имени возвращает старое имя с тем же userId/key, потому что1.5 требует точного совпадения nickname ответа с запросом. Новые клиенты получают каноническое имя через18 и показывают подтверждённое переименование. Эта политика нужна для сохранения доставки/доверия старых контактов.

Запрос17 содержит schema1, неизменный userId, old/new nickname по действующей Limits.nickname, requestUUID, monotonically increasing nameRevision и подпись identity над доменно разделёнными байтами `AEGIS-NICKNAME-CHANGE-v1`. Сессия обязана принадлежать тому же userId. Сервер в одной транзакции сохраняет уникальный requestUUID/payload hash, old alias reservation, canonical name и owner-signed binding. Точный повтор возвращает прежний commit; конфликт requestUUID, занятое имя, старая revision или чужая сессия отклоняются. Ответ echo-ит подписанный binding после commit; он не требует release key/нового server signing key.

Публичные профили старых aliases требуют отдельного совместимого поведения: новый клиент после rename публикует подписанные версии для своих aliases (включая скрытие/удаление), иначе1.5 не сможет проверить профиль с новым nickname. Сервер принимает alias-profile только от сессии того же закреплённого userId; old profile-get формат сохраняется. Это увеличивает число публикаций пропорционально aliases; предусмотреть лимит переименований/rate limit без переиспользования старых имён. Новые18-ответы не дают права переписывать исторические подписи писем.

Клиент до server commit сохраняет snapshot. После подтверждения атомарно меняет canonical name, nickname-indexed avatar/profile/friend metadata, сохранённую сессию и необходимые AAD-sidecars, используя прежний локальный ключ шифрования. Исторические пакеты/receipts и identity не меняются. Recoverable journal позволяет завершить повторно либо восстановить snapshot после сбоя; при потере ответа повторяется тот же requestUUID. Отключённый/старый сервер оставляет nickname read-only и сохраняет все прежние операции.

Разрешение требуется на **этот дополнительный протокол, политику постоянных aliases и staging-миграцию**. Production deployment и изменение production БД остаются отдельным последующим разрешением после staging evidence. До такого согласования код16–18/БД/production не изменяются — это следует из §39 ТЗ о существенных изменениях протокола, а не из обычного разрешения на UI-правки.
