# Безопасность АЕГИС 1.0.0

Этот проект не проходил независимый криптографический аудит. Перед использованием для чувствительных данных требуется проверка реализации и обязательная приёмка на целевых ОС. Сборка и локальные тесты не означают доказанную безопасность.

## Защищённые письма

Текст дополнительно защищён FF1 и AES-GCM с двумя независимыми секретами. Вложения и тема остаются в существующем E2EE; дополнительные секреты не защищают файл. FF1 не проверяет правильность кода; узнаваемый текст может помогать перебору. См. CRYPTO-1.0.0.md.

## Что шифруется

Обычное сообщение и имя/содержимое вложения шифруются AES-256-GCM со случайным 256-битным ключом и случайным 96-битным nonce. Ключ упаковывается стандартным libsodium sealed box отдельно для получателя и отправителя. Ed25519-подпись связывает весь внешний пакет. Relay не получает приватные ключи или пароль vault.

Чтобы сохранить существующие 44-байтные Ed25519 public keys аккаунтов protocol 1, применяется документированное libsodium преобразование Ed25519 → Curve25519. Это необходимо для автоматического E2EE без новой регистрации и изменения relay wire protocol. Криптографические операции выполняют JCA и libsodium, собственный криптоалгоритм не реализуется. Формат контейнера приложения описан в PROTOCOL.md.

**Forward secrecy нет.** Кража долговременной приватной идентичности может раскрыть сохранённые старые пакеты. Копия ключа отправителя тоже может открыть исходящие сообщения. Double Ratchet, post-compromise security и синхронизация нескольких устройств не реализованы. Не представлять этот проект как эквивалент Signal.

## Проверка контактов

Relay сообщает публичный ключ контакта, который закрепляется локально. При добавлении нужно сверить SHA-256 fingerprint через независимый канал. Подмена ключа после закрепления блокирует отправку. Компрометированный relay может подменить ключ при первом знакомстве, если отпечаток не сверили; одна криптография этого не исправляет.

Получатель принимает только подписанные пакеты доверенных контактов. До добавления отправителя письмо остаётся на relay и TTL доставки продолжается. Оба пользователя должны добавить друг друга.

## Пароли и локальные данные

Пользователь вводит один пароль аккаунта/локальных данных. Relay protocol 1 получает прежний пароль через Tor и хеширует его со своей солью; wire auth не изменён. Vault использует отдельную случайную соль и Argon2id Additional context AEGIS-VAULT-v1 (v19, 64 MiB, 3 прохода, 1 lane) → AES-256-GCM. Derived vault key серверу не передаётся. Компрометированный relay может перехватить исходный account password при входе: при дополнительной краже локального vault он позволяет открыть и его. Domain separation не устраняет риск повторного применения исходного пароля. Слабый пароль допускает offline brute force при краже файлов. Мастер-пароля и recovery master key нет.

Backup содержит уже зашифрованный state.vault и соль. Новый AEB2 backup требует пароль аккаунта на момент экспорта; старый AEB1 требует старый пароль vault. Он не содержит историю сообщений. Потеря и vault, и backup означает потерю идентичности; пароль аккаунта не восстанавливает ключ.

Java не гарантирует уничтожение всех копий String в RAM. Приложение стирает доступные byte/char arrays и очищает элементы UI, но ОС, swap, crash dumps, дамп процесса, clipboard manager, кейлоггер, скриншот и камера остаются вне его контроля. Heap dumps и attach отключены флагами launcher; это не защита от владельца/администратора устройства.

Windows: файлы vault ограничиваются ACL текущего пользователя, POSIX: каталог 0700/файлы 0600. Запись выполняется через forced file и atomic rename. Java NIO не предоставляет эквивалент directory fsync на Windows: после внезапного отключения питания окончательная гарантия зависит от NTFS/оборудования. Reboot/power-loss испытание в этой среде не проводилось.

## Скачанные вложения

Несколько вложений защищены прежним E2EE; дополнительный AES/FF1 envelope защищает только текст. GUI разрешает скачать вложения защищённого письма после правильного letter password. Получатель, контролирующий код/ключ E2EE клиента, может извлечь файл без этого GUI; не считать пароль письма дополнительным криптографическим слоем над передаваемым файлом.

Экспорт создаёт WinZip AES-256 AE-2 ZIP потоками Zip4j. На диск идут только зашифрованные bytes; пароль не добавляется к сообщению или metadata. Пароль хранится в char[] открытого view и стирается при закрытии; работающий export имеет собственную временную копию, очищает её finally и удаляет частичный ZIP при отмене/TTL. Java String/UI/GC абсолютного стирания не гарантируют.

Совместимый ZIP имеет PBKDF2-HMAC-SHA1 с 1000 итерациями, AES-CTR/HMAC, а не Argon2id. Поэтому его пароль существенно легче проверять offline, чем пароль letter envelope; используйте сильный пароль. Имена/размеры файлов в ZIP headers видимы. Формат: https://www.winzip.com/en/support/aes-encryption/ . Экспортированный ZIP и чужие резервные копии не контролируются TTL. Существующий destination никогда не перезаписывается. Файлы не запускаются и архивы не распаковываются автоматически.

## TTL

После durable приёма ciphertext получатель создаёт подписанный ACK. Время первого приёма закрепляется и не меняется при дубликате. TTL идёт независимо от открытия текста. ACK удаляет relay-копию, а delivery deadline удаляет недоставленное письмо. Повторный пакет не возвращает уже удалённую локальную запись.

При закрытом приложении оно не исполняет таймер: просроченные encrypted files удаляются при следующем запуске/разблокировке (старый опциональный Linux cleanup timer также поддержан). Когда приложение открыто, cleanup работает раз в секунду. Обещания физического стирания SSD, резервных копий ОС или информации, переписанной человеком, нет.

Для исходящей локальной копии P2P ACK даёт точное время доставки. Старый relay не возвращает отправителю статус последующего offline ACK: GUI честно показывает «На сервере · подтверждение недоступно». Такая копия у отправителя истекает от отправки через выбранный TTL; получатель отсчитывает свой TTL от фактического приёма. Обновлять протокол ради неподтверждаемой галочки доставки не стали.

## Сеть и пределы защиты

Tor unavailable → offline. Java не разрешает IP/clearnet адрес relay и не выполняет DNS для onion. Tor/Snowflake сами создают необходимые внешние соединения, перечисленные в README. Это не обещание абсолютной анонимности: ISP видит факт Tor либо обходного транспорта; сильный противник может анализировать время/объём трафика.

Компрометация relay позволяет удалять, задерживать, повторять пакеты, видеть служебные метаданные и перехватывать пароль аккаунта при входе. При корректно проверенных идентичностях она сама по себе не даёт ключи содержимого. Компрометация клиента может раскрыть всё, что видит клиент.

## Ограничение ресурсов

Версионируемый bounded binary codec без Java native serialization. Ограничены текст, вложения, пакеты, число пользователей, очередь и потоки. Есть rate limiting авторизации, дедупликация, проверка подписей и TTL, резерв свободного диска. Файлы не распаковываются и не просматриваются автоматически; traversal, Windows device names и ADS отклоняются.

Обнаруженную уязвимость обсуждайте с владельцем своей установки по доверенному каналу. Автоматического отправления отчётов и внешнего security endpoint нет.

## Устройство и система обновлений

Remember-login хранит в OS storage только случайный 32-байтный device key. DPAPI использует CurrentUser, не LocalMachine; Linux обращается к Secret Service через libsecret с ограниченным временем ожидания. Этот ключ шифрует AES-GCM envelope с vault unlock key и существующим relay bearer. Пароля аккаунта, letter password и FF1 в envelope нет. Device-bound session не является portable backup. Другой процесс того же OS user или скомпрометированная ОС могут получить доступ: DPAPI/KWallet не защищают от полного захвата пользовательской сессии.

Срок локального unlock — 7 дней, expiry и перевод времени назад инвалидируют envelope. Relay 0.2.0 хранит 12-часовые sessions только в RAM. Беспарольная сетeвая reauthentication после их expiry/reboot без сохранения account password или изменения relay невозможна. AEGIS-AUTH-v1 client-derived authentication material также изменил бы пароль для существующих server hashes. Поэтому server auth сохранён, vault KDF отделён. Эти два буквальных требования ТЗ не отмечаются выполненными.
