# Управление сервером из Core 6.0.0

`ManagementClient600` использует только существующий `TorTransport`: onion отправляется в loopback SOCKS, локального DNS, HTTP redirects и прямого fallback нет. Публичный файл `core600/management.properties` содержит ровно `onion`, `port`, `publicKey` (Ed25519 X.509, Base64URL). Повторяющиеся/неизвестные поля и symlink отклоняются. Закреплённый Identity public key передаётся независимо из настроек Core.

Для каждой операции Core вызывает `GrantProvider.acquire(exactRequest)`: повторная аутентификация остаётся в Почте, Core получает AEGIS capability со scope ACCOUNT_READ/ADMIN и собственный app proof key. Root identity private key не передаётся Management Agent. Клиент проверяет issuer, срок, app/scope и соответствие proof key, но решение о полномочиях всегда повторяет broker через текущий Identity account/device/generation/role/step-up. Локального признака «администратор» недостаточно.

Метаданные — точный `ManagementPolicy.Request` wire v1: `DataOutputStream.writeUTF` для домена, canonical UUID, enum action, enum service или пустой строки, immutable 64-hex snapshot или пустой строки. Клиентский формат не импортирует server classes и сверяется тестом с настоящим `ManagementPolicy.decode` для всех разрешённых служб и действий. `MAIL_RELAY` означает только новый `aegis600-staging-mail-relay.service`; production Relay не входит в allowlist.

HTTP POST `/management/v1` содержит bounded JSON `{metadata,proofs}`. App PoP подписывает `IdentityProtocol.requestDigest` точного SHA-256 метаданных и action. Ответ подписан сервисом через `IdentityProtocol.response(servicePinHash,firstProofNonce,exactEnvelope,exactReply)`. Клиент проверяет подпись до чтения результата, отклоняет неоднозначные headers, лишние поля и oversized JSON. Одновременно выполняется одна операция, общий deadline 60 секунд, активные сокеты закрываются при выходе/блокировке раздела. Автоматического повторения команды после неопределённого результата нет.

Лимит публичного агента — 30 запросов в минуту, 2 workers и очередь 8. Корректно декодированный 31-й запрос получает подписанный HTTP 429, привязанный к исходным bytes/nonce; broker не вызывается и proof не потребляется. Клиент возвращает отдельный `Busy`, интерфейс показывает понятный русский статус. Задание backup/restore принимается асинхронно: принятие systemctl-команды не является результатом внешней резервной копии.

API `approve(Request,Grant)` / `executeApproved(Request,List<Approval>)` поддерживает два независимых действующих администратора для восстановления. Обе подписи относятся к одному UUID/action/snapshot, срок ≤120 секунд. Повтор одного account ID, изменённые метаданные и replay отклоняются клиентом и независимо сервером. Встроенная компактная панель реализует состояние, подтверждённый перезапуск и создание копии; обмен двумя restore approval не выдается за готовый пользовательский диалог. Сам restore создаёт отдельный проверенный каталог, не переключает рабочие данные автоматически.

Фактические локальные доказательства: production HTTP handler, production TorTransport через явно локальный SOCKS fixture, настоящий Identity HTTP/SQLite, Owner и четырьмя подписями делегированный второй администратор. Systemctl заменён открыто обозначенным recorder. Это не public Tor, native UID broker, systemd/AppArmor или offsite restore. Эти gates остаются NOT_RUN, `productionReady=false`.

Предполагается один логический Management Service на Identity issuer. Отдельные независимые среды должны иметь разные Identity issuer либо дополнительную service-audience привязку тела запроса перед совместным использованием issuer. При полном root-контроле над VPS защита серверных ключей и аудита не гарантируется. Отзыв запрещает новые операции, но не отменяет уже применённую системную команду.
