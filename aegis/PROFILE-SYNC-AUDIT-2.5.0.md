# АЕГИС 2.5.0: аудит публичных профилей и аватаров

Дата аудита: 2026-10-15. Проверен commit `f173b4a1bb5f1e3ed121870aa04a6583833f93e9`, ветка `development/aegis-2.5.0`, унаследованная от удалённой базы 2.0.0. Это чтение исходников и уже сохранённых доказательств. В рамках данного аудита новые сборки, тестовые аккаунты, сетевые запросы и изменения production Relay не выполнялись.

## Фактическая архитектура

| Уровень | Реализация в проверенной базе |
|---|---|
| Capability | `CAPABILITIES(11)` возвращает маску; bit 1 разрешает профили, bit 2 — подписанные contact assertions. Проверенный исходник Relay возвращает 3. Фактический ответ production Relay не установлен. |
| Передача | `PROFILE_PUT(12)` публикует подписанный `PublicProfile`, `PROFILE_GET(13)` получает его по nickname. Операции требуют аутентифицированной Relay-сессии. Клиент использует `TorTransport`; отдельного прямого HTTP/image URL нет. |
| Подпись | Ed25519 identity подписывает домен `AEGIS-PUBLIC-PROFILE-v1`, userId, nickname, revision, visible, about, avatar и publicKey. Приватный ключ и пароли в payload не входят. |
| Проверка сервера | Relay сверяет владельца сессии, nickname/userId/publicKey, подпись и revision; более старая версия и конфликтующее содержимое той же revision отклоняются. Сервер не декодирует пиксели. |
| Проверка клиента | `NetworkService.profile` сверяет ответ с каталогом и проверяет подпись; `LocalStore.cacheProfile` дополнительно требует заранее закреплённый контакт и проверяет его identity key, подпись и revision. |
| Хранение | `profiles/<userId>.enc` зашифрован локальным ключом vault с AAD `profile/v1/<userId>`. Сохраняется исходный подписанный payload. Для отображения `avatar(remote)` декодирует и нормализует изображение. |
| Отображение | Карточки используют изображения проверенного кэша. Просмотр профиля выполняет синхронизацию, затем читает пиксели повторно. Отсутствующий аватар даёт инициалы, а не изображение владельца локального аккаунта. Крупный просмотр работает через `AvatarViewer`. |
| Обновление | `ClientSession.syncPublicData` публикует локальное изменение с большей revision и обновляет один контакт за цикл; штатный poll имеет задержку 15 секунд. Явный просмотр контакта запрашивает его сразу. |

При стандартном лимите 32 контакта один круг фонового обновления может занимать около восьми минут плюс сетевые задержки. Это наблюдение по алгоритму, а не измеренный предел времени синхронизации.

## Публичность и обработка изображений

- Для новых `LocalFeatures` действуют `visible=true` и `profilePending=true`. Сохранённое значение публичности существующего пользователя читается из зашифрованного sidecar и не заменяется новым default.
- При `visible=false` `Identity.profile` подписывает пустые about и avatar. Получение новой скрытой версии заменяет кэш и прекращает показ старого аватара.
- Получатель без сети сохраняет последнюю подписанную версию. Удалённо отозвать уже полученные пиксели у офлайн-получателя невозможно. Экран профиля обозначает сохранённую подписанную версию; контактные миниатюры отдельного индикатора свежести не имеют.
- Исходный локальный файл ограничен 2 МиБ. Разрешены PNG/JPEG/WebP, обычные файлы без symlink. Измерения проверяются до полного декодирования: не более 4096 по каждой стороне и 16 777 216 пикселей; выход — PNG 256×256.
- В этой базе `LocalStore.avatar` нормализует пиксели до записи, а `ClientSession.syncPublicData` повторно нормализует старые сохранённые изображения перед подписью и передачей. Поэтому штатный publisher не передаёт исходные EXIF/GPS-метаданные.
- Протокол ограничивает avatar 1 МиБ, description — 500 символами. Клиент проверяет декодирование даже правильно подписанного чужого изображения. Это не утверждение о формально доказанной безопасности стороннего декодера.
- `Identity.profile` остаётся низкоуровневым подписывателем и сам по себе не очищает произвольные переданные байты. Новые production callers обязаны использовать ту же проверенную цепочку нормализации.

## Конкретные дефекты и действия

Все пункты ниже установлены чтением указанного commit; воспроизведение новых failure cases в этом аудите **NOT_RUN**.

### PS-25-01 — новый аватар и признак необходимости публикации записываются раздельно

При выборе/удалении аватара `MessengerApp` сначала выполняет `LocalStore.avatar`, затем `LocalFeatures.profileChanged`. Эти операции изменяют разные зашифрованные файлы. Если приложение завершится после первой записи либо вторая запись завершится ошибкой, после перезапуска новый локальный аватар может остаться при ранее сохранённом `profilePending=false`. Изменение не будет опубликовано штатным условием `pending()`.

Рекомендация: локальная crash-safe фиксация dirty-состояния вместе с изменением аватара либо проверка локального нормализованного hash/visibility/about против последнего подписанного собственного кэша при открытии аккаунта. Сетевой протокол, identity key и production Relay для такого исправления менять не требуется. Нужны тесты прерывания между записями и восстановления после отказа диска.

### PS-25-02 — профильный кэш не входит в локальную квоту, удалённые контакты оставляют записи

`LocalStore.usedBytes` считает mail, sent и lifecycle. `cacheProfile` и запись собственного аватара не проверяют `maxBytes`. `removeContact` удаляет nickname-аватар старого формата, но не `profiles/<userId>.enc`. Поэтому кэш способен превысить настроенную квоту; последовательное добавление/удаление разных закреплённых контактов сохраняет orphan-записи без отдельного лимита.

Рекомендация: отдельная ограниченная квота для профилей/аватаров с атомарной заменой и учётом размера прежней записи; согласованное удаление либо ограниченная политика retention при удалении контакта. Не удалять письма или identity ради очистки кэша. При отказе новой записи сохранять последнюю проверенную версию.

### PS-25-03 — маска capability 2 допускает сообщение об успешной синхронизации профилей

`ClientSession.syncPublicData` обрабатывает специальным статусом только `capabilities==0`. При допустимой маске 2 публикация/получение профиля пропускаются, но `profileSynced` остаётся true и конечный текст сообщает «Публичные данные синхронизированы». Пользователь может считать свой аватар опубликованным, хотя bit 1 отсутствует, а локальная публикация остаётся pending.

Рекомендация: явно показывать отсутствие profile capability независимо от поддержки contacts, сохранять pending и отдельно отражать успех доступных операций. Это клиентское исправление без изменения Relay.

### PS-25-COMPAT — расширение capability в 2.5.0 требует совместимого согласованного формата

`NetworkService.capabilities` отвергает любые биты вне маски 3. Нельзя просто включить новый bit в существующий ответ 11 ради звонков/rename: это сломает клиентов текущего формата. В новой архитектуре следует использовать отдельно согласованное версионированное расширение с fallback на действующий ответ. Это ограничение совместимости, а не разрешение на серверную правку.

## Условия последующей приёмки

После клиентских исправлений выполнить новые тесты на зафиксированном commit: crash-safe avatar dirty state; квота и очистка профилей; маски capability 0/1/2/3; конкурирующее изменение аватара/публичности; изменение/удаление/скрытие после offline restart; повреждённый и чрезмерный payload; сохранение identity/писем/архива.

Отдельно выполнить staging A/B через настоящий Tor с новым onion, не изменяя production: публикация, получение, изменение, скрытие, удаление, повторный вход и persistence Relay. Владелец должен отдельно согласовать любые серверные/протокольные изменения. На данном этапе нет оснований объявлять live Tor profile sync или нативную приёмку 2.5.0 пройденными.

## Клиентские исправления после аудита

По отдельному поручению root исправления PS-25-01/02/03 внесены в рабочее дерево 2.5.0 поверх указанной базы. Они ещё не означают принятую полную сборку 2.5.0 и не меняют production Relay.

- **PS-25-01 — FIXED_LOCAL / targeted PASS.** До записи или удаления пикселей атомарно сохраняется небольшой зашифрованный журнал `own-avatar-publication-v1.vault` с уникальным nonce. `LocalFeatures.ProfileState` захватывает nonce; подтверждение публикации удаляет только совпадающий журнал. Новый аватар, появившийся после начала публикации, остаётся pending. После перезапуска наличие журнала восстанавливает необходимость публикации даже без вызова UI `profileChanged`; повреждение журнала трактуется консервативно как необходимость повторной публикации. Rekey переносит журнал с новым локальным ключом, сохраняя identity.
- **PS-25-02 — FIXED_LOCAL / targeted PASS.** Зашифрованные profiles и avatars включены в локальную квоту. Отказ роста не заменяет прежние проверенные данные и не создаёт новый dirty nonce. Удаление контакта удаляет его profile cache; открытие хранилища очищает well-formed orphan-записи прежних версий, сохраняя собственный профиль и текущие закреплённые контакты. Письма не удаляются.
- **PS-25-03 — FIXED_SOURCE / compile PASS.** Конечный статус отдельно сообщает отсутствие bit 1 даже при поддержке contacts. Новый wire/capability не добавлялся. Отдельная новая wire-проверка маски 2 пока NOT_RUN.

Выполнена изолированная Java 21 компиляция фактически изменённых `LocalStore`, `LocalFeatures`, `ClientSession` и выбранных тестов против имеющихся базовых зависимостей. Это не полная пересборка всех параллельно изменяемых модулей 2.5.0. Результат [JUnit](docs/test-results/2.5.0-profile-followup/TEST-junit-jupiter.xml): **17/17 PASS**, 0 failures/errors/skips, 7,542 секунды.
