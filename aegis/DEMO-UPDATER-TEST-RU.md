# АЕГИС 1.1.1 Demo: подпись, публикация и настоящее испытание updater

Цель — обновить **уже установленную опубликованную 1.1.0**, а не вручную установить 1.1.1. Тест завершён только когда сам клиент получил подписанный manifest через свой Tor, скачал пакет, проверил его, заменил приложение, перезапустился и сохранил профиль.

## Канал и ограничения

В опубликованной 1.1.0 уже есть Настройки → Обновления → Канал → **Beta**. Этот выбор сохраняется в существующем `update-preferences.json`. Клиент запрашивает фиксированные `main/updates/beta.json` и `beta.json.sig` в том же репозитории; отдельный URL или другой public key не поддерживается. Проверка Ed25519 выполняется до разбора JSON, floor и история разделены по каналам.

Поэтому используем **существующий Beta**, версию `1.1.1`, тег `v1.1.1` и optional policy. Stable и production Relay не меняются. Публикация Beta — отдельное явное действие владельца после подписи. Если канал Beta используется другими людьми, они тоже увидят Demo при включённых проверках; это не персональный секретный канал. До размещения обоих файлов Beta выдаёт понятную ошибку отсутствующего feed, что ожидаемо.

Для произвольного третьего канала без изменения бинарника 1.1.0 поддержки нет. HTTPS proxy, подмена DNS/TLS, новый ключ или отключение проверки подписи не используются.

## 1. Офлайн-подпись владельцем на CachyOS

Распакуйте финальный `AEGIS-1.1.1-Demo-offline-signing-bundle.zip`. Приватный ключ остаётся на вашей офлайн-машине/носителе, **вне каталога пакета**. Интернет и GitHub при подписании не нужны. Python 3.11+ и OpenSSL 3 нужны только владельцу, не пользователям приложения.

Из каталога `AEGIS-1.1.1-Demo-offline-signing`:

```bash
sha256sum --check BUNDLE-SHA256SUMS
sha256sum --check SHA256SUMS
sha256sum --check SIGNING-INPUT-SHA256
python3 tools/sign-release-manifest updates/beta.json /путь/на/офлайн-носителе/aegis-ed25519-private.pem
python3 tools/verify-release-manifest updates/beta.json updates/beta.json.sig --assets . --minimum-version 1.1.0
```

Точная эквивалентная OpenSSL-команда:

```bash
openssl pkeyutl -sign -rawin -inkey /путь/на/офлайн-носителе/aegis-ed25519-private.pem -in updates/beta.json -out updates/beta.json.sig
openssl pkeyutl -verify -rawin -pubin -inkey updates/release-public.pem -in updates/beta.json -sigfile updates/beta.json.sig
```

Предпочтителен Python helper: он проверяет соответствие ключа уже закреплённому public key. Не создавайте новый ключ. Подпись должна содержать ровно 64 байта. Перед переносом на онлайн-машину выполните вторую Python-проверку вместе с `--assets`. После подписи ничего не меняйте в JSON, SHA256SUMS, changelog или binaries. Любая пересборка требует новых хешей, manifest и подписи. Старые 1.1.0 signatures не подходят. Перенесите только пакет и `beta.json.sig`, никогда private key.

## 2. Публикация только владельцем

Сначала проверьте подпись и SHA ещё раз на онлайн-машине. Убедитесь, что `v1.1.1` не существует; существующий выпуск не перезаписывайте. В GitHub создайте Release с tag `v1.1.1`, target — commit из финального BUILD-PROVENANCE.json, названием «АЕГИС 1.1.1 Demo», отметкой **Pre-release**. Вставьте RELEASE-NOTES-GITHUB.md.

Загрузите все четыре обязательных manifest artifacts (Setup, portable ZIP, AppImage, **client-source.zip**), `SHA256SUMS`, `CHANGELOG-1.1.1.md`, `AEGIS-1.1.1-source.zip`, отчёт и инструкции. Файл `client-source.zip` обязателен даже если рядом есть `source.zip`. Можно приложить `beta.json` и его подпись для аудита; updater получает их из `main/updates`, а не Release assets.

Сначала опубликуйте доступные assets, затем **одним commit** добавьте `updates/beta.json` и `updates/beta.json.sig` в `main`. Это обеспечивает согласованную пару; возможное краткое рассогласование CDN завершится отказом подписи, а не установкой. Не редактируйте `updates/stable.json`, `stable.json.sig`, public key и server config. Здесь нет команды автоматического изменения feed или публикации.

Клиент 1.1.0 допускает точные URL только из:

`https://github.com/Babmoleilo90210/AEGIS-Releases/releases/download/v1.1.1/ИМЯ_ФАЙЛА`

Draft assets недоступны обычному приложению. Финальные прямые ссылки находятся в RELEASE-NOTES-GITHUB.md; они начнут работать после вашей публикации.

## 3. Подготовка нативных испытаний

Используйте отдельную Windows 11 VM/учётную запись и отдельную CachyOS KDE учётную запись или VM. Сохраните cold VM snapshot. Создайте отдельные тестовые аккаунты на вашем Relay; не меняйте его конфиг/onion identity и не открывайте порты. Не запускайте две копии одного identity одновременно. Проверяйте Wayland и X11 отдельно.

Исходная сборка — публичная **1.1.0** из v1.1.0, не кандидат и не 1.1.1. Windows Setup SHA-256:

`1d12f8f0c488e65dc189f59ddeeb5dff9e6387023e2f50e4ca535e7c2102c261`

CachyOS 1.1.0 AppImage SHA-256:

`41269908cf47e1e91e3e0a61b1213fbd92263271aa3c3e209145abb68f8707d0`

Windows: установите 1.1.0 штатным Setup от обычного пользователя. Целевой каталог updater — `%LOCALAPPDATA%\Programs\AEGIS`. Portable updater также устанавливает в этот штатный каталог; исходная распакованная копия остаётся прежней. Для доказательства штатного сценария тестируйте Setup и запускайте установленный ярлык.

CachyOS: в новой тестовой учётной записи разместите исходную 1.1.0 как `~/.local/opt/aegis/AEGIS.AppImage` и разрешите исполнение. Updater заменяет именно этот стабильный путь. При нестандартном `XDG_DATA_HOME`/`XDG_CONFIG_HOME` сохраняйте исходные значения на протяжении теста. AppImage требует поддерживаемый GUI/FUSE; предусмотренный `--appimage-extract-and-run` допустим как отдельный сценарий и не доказывает обычный mount.

Создайте тестовые письма с достаточным TTL (например, один день), контакт с проверенным fingerprint, отправленный/входящий файл, выбранный старый theme/layout и, при наличии, сохранённую сессию. Запишите только версии, количество писем и fingerprints, без паролей, plaintext или private keys.

Полностью закройте AEGIS и свой Tor. Сохраните **весь** профиль, внешний client config, старые binaries и VM snapshot: Windows `%LOCALAPPDATA%\AEGIS` и `%LOCALAPPDATA%\Programs\AEGIS`; CachyOS `${XDG_DATA_HOME:-$HOME/.local/share}/aegis-app`, `${XDG_CONFIG_HOME:-$HOME/.config}/aegis`, `~/.local/opt/aegis`. Identity backup не заменяет backup профиля. Сессия DPAPI/Secret Service привязана к OS-пользователю и не обещается переносимой на другую машину; VM snapshot сохраняет OS credential state.

## 4. Положительный переход 1.1.0 → 1.1.1

1. Запустите установленную 1.1.0, войдите и убедитесь, что обычная почта работает. Не запускайте Demo вручную.
2. Настройки → Обновления → **Beta**. Включите автоматическое скачивание и нажмите «Проверить обновления».
3. Убедитесь, что появляется **одно** системное письмо о 1.1.1 Demo; повторная проверка не создаёт дубликат. Отправьте ещё обычное письмо: канал обновлений не меняет OnionTrafficOnly почты.
4. Наблюдайте реальные MB/проценты. До «готово к установке» кнопка установки недоступна. В диагностике не должно быть ошибок подписи, TLS, schema или SHA.
5. Для resume прервите только собственное соединение/процесс приложения в тестовой VM во время скачивания, затем запустите 1.1.0 повторно, выберите Beta и повторите проверку. `.part` сохраняется; корректный Range продолжает загрузку, серверный HTTP 200 допускает безопасное начало заново. Наличие частичного файла само по себе не доказывает resume — сопоставьте его размер с первым новым byte progress. Не вмешивайтесь в чужой Tor и не отключайте TLS.
6. После полного скачивания подтвердите установку в единственном окне. Проверьте создание `backups/pre-update-*` с проверяемым snapshot inventory, содержащим vault/config/settings/avatars/mail/sent/receipts/sessions и Tor state. Там нет plaintext staging.
7. После restart разблокируйте хранилище **в течение 10 минут**: подтверждение успешного старта требует vault, UI и локальной crypto self-check. Одно появление окна не считается успешной установкой.
8. О программе показывает **1.1.1**. Сверьте fingerprints, контакты, письма, вложения, сроки TTL, receipts и настройки. TTL продолжает идти и не продлевается обновлением. Сессия остаётся в пределах возможностей защиты ОС; при необходимости выполните штатный вход.
9. Настройки → Внешний вид → Тема → **Тёмно-зелёная**. Проверьте Profile, почту, composer, настройки, updater и внутренний просмотр в одном окне; выберите «Как в системе» и старую тему, затем снова зелёную. Черновик сохраняется.
10. Закройте и откройте AEGIS; зелёная тема сохраняется, повторного предложения 1.1.1 нет. Проверьте переписку Windows ↔ CachyOS, offline delivery, TTL и файл. Отдельно перезагрузите каждую тестовую ОС.

## 5. Безопасное испытание rollback

Восстановите исходный **полный cold VM snapshot 1.1.0** в тестовой машине. Не откатывайте production-профиль и не редактируйте update floor в рабочем приложении. Повторите штатную загрузку Demo и подтвердите установку. После появления новой 1.1.1 **не разблокируйте хранилище**, сразу закройте её окно и оставьте detached updater завершить 10-минутный срок ожидания. Startup ACK не должен появиться.

Ожидается возврат прежних binaries, восстановление совместимого full profile и запуск 1.1.0. Если не произошло — зафиксируйте FAIL, сохраните cold snapshot и transaction `failed` marker/безопасную диагностику, прекратите выпуск. Не удаляйте `.old` вручную. Не изменяйте candidate EXE/JAR, подписанный ZIP или manifest ради rollback: это проверяло бы другую цепочку и нарушило SHA.

Проверка неверной подписи/хеша и path traversal выполняется тестовыми helper/unit fixtures, без изменения опубликованного Beta и private key. Эти тесты отдельно указаны в отчёте; они не заменяют нативную установку и rollback.

## 6. Критерии PASS и отчёт

Для Windows 11, CachyOS Wayland и X11 заполните строки: исходный SHA/version, Tor mode/100%, единственная копия системного письма, actual progress, resume, pinned Ed25519, size/SHA/package, confirmation, full backup, restart, vault/UI/crypto ACK, итоговая version, fingerprints/state/TTL, theme persistence, reboot, failed-start rollback. Не включайте реальные сообщения, пароли, Tor cookie или private keys в отчёт.

Direct Tor и Snowflake проверяются раздельно штатными расширенными настройками соединения в тестовой учётной записи. Обход неудачи прямым интернет-соединением запрещён. Без каждой фактически пройденной нативной строки нельзя объявлять полный E2E или `productionReady=true`.

До владельческой подписи/публикации Demo остаётся **unsigned candidate**, native signed E2E — **NOT_RUN**. Stable 1.0.0, оставшийся в main на момент подготовки, нормально отображается как «новых обновлений нет» у 1.1.0/1.1.1; это не ошибка Tor.
